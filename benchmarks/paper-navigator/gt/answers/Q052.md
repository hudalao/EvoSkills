# 公司内部使用代码生成 Agent 的治理设计：权限边界、代码安全与责任审计

（证据范围：2024 年至今；以 ICSE/FSE/MSR/TOSEM/IST/FAccT/IUI 等软件工程与治理场域的实证与框架研究为主）

---

## 〇、先把问题定准：内部代码 agent 到底改变了什么

治理设计如果照搬"AI 补全插件"的老规矩，一定会失效。近两年的实证研究显示，编码 agent 相对于早期补全工具发生了三个结构性变化：

1. **产出规模与形态变了**。对 GitHub 上 agent 参与的 PR 做的大规模实证发现，agent 生成的变更已经成为常规贡献形态，而不再是零星片段，其被合并与被拒绝的模式与人类 PR 存在系统性差异[1]。
2. **触碰的资产变了**。MSR 的实证研究专门统计了 agent 对 CI/CD 配置文件的修改频率与成功率，说明 agent 已经在动"构建与发布的控制面"，而不只是业务代码[2]。
3. **组织瓶颈变了**。一项对企业强制推行"AI 产出翻倍"指标的纵向案例研究显示，产出速度提升之后，真正的约束点转移到了人工评审容量上——"写得比看得快"成为落地后的主要结构性风险[3]。

因此，内部治理的对象不是"一段生成的代码"，而是"一个会自己调用工具、修改仓库、触发流水线的自治执行体"。近期对 code agent 安全的专门综述也把攻击面、防御与评估三块合并讨论，指出该领域的防御研究高度碎片化、缺乏统一评测口径[4]。

---

## 一、治理框架：一条"分级—约束—验证—留痕—追责"主线

建议按五个环节搭建，每个环节都要有可执行的技术控制点，而不只是制度文档。

### 1.1 环节 A：风险分级与准入（决定"这个 agent 配拿多大权限"）

- **对内部自建 agent 做风险分层**。TrustX ARC 框架专门针对"企业内部自研的 agentic AI 系统"提出风险分级方法，把自治程度、可触达资产、可逆性等维度组合成风险层级，用层级决定后续管控强度[5]。这比一刀切的"允许/禁止"更适合内部工程场景。
- **把治理落到运行时，而不是只落到审批表**。MI9 提出了面向 agentic AI 的一体化运行时治理框架，强调治理能力必须在 agent 运行过程中持续生效（行为约束、监控、干预），而非部署前一次性评审[6]。
- **承认防御知识本身尚未成熟**。code agent 安全综述指出，现有防御与评估方法之间缺乏可比性，企业不应假设"接了某个安全组件就安全了"[4]。

**落地建议**：内部把 agent 分成三档——① 只读/建议档（可读代码、只产出 diff 建议）；② 受限写入档（可在隔离工作副本写入、可提 PR、不可直接合并、不可动 CI/CD 与密钥）；③ 高自治档（可执行长时程任务，但必须在硬化环境中且全程留痕）。档位由 ARC 式风险分级决定[5]，档位变更走变更管理流程。

### 1.2 环节 B：权限边界（身份 → 授权 → 能力 → 隔离）

这一层是整个治理的地基，学术界近两年的进展最集中，可以分四个子问题设计。

**(1) 身份与委托：agent 必须"代表谁"是可验证的**

- Authenticated Delegation 提出了面向 AI agent 的认证委托与授权框架，核心主张是：必须能验证 agent 代表哪个主体行动、被授予了什么范围，并把这一委托关系变成可核验的凭证[7]。这直接对应企业内部的"agent 不能共用一个万能服务账号"。
- 企业侧已有可参考的工程实践：一项企业身份集成的架构与案例研究，把 AI 开发者服务接入既有的身份、访问控制与治理体系（含 MCP 场景），说明"agent 身份纳入 IAM"是可实现的，而不是理论主张[8]。

**(2) 授权：最小权限要能被强制，而不是靠提示词自觉**

- Progent 提出对 AI agent 的特权控制机制，用策略对工具调用做细粒度授权，抵御间接提示注入导致的越权动作[9]。
- 更强的一条路线是把操作系统里的强制访问控制（MAC）思想搬进 agent 系统：该工作系统性刻画了 LLM agent 系统中的多种提权路径，并给出强制访问控制框架来收敛过度授权[10]。
- 授权设计要有实证依据。FSE 2026 的一项工作专门评测了 agent 在真实工具集上的**特权使用情况**，衡量 agent 实际需要多大权限、以及超额授权的普遍程度[11]，这类数据是企业裁剪权限清单的直接依据。

**(3) 能力：权限要能到期、能撤销、能按副作用分类**

- Lingering Authority 针对编码 agent 提出"可撤销的资源与副作用能力"模型，核心问题是：任务结束后 agent 手里残留的授权（token、句柄、已建立的连接）会长期滞留形成风险[12]。企业内部尤其要注意"一次任务授权、长期有效"的默认实现。
- 可验证的工具使用是更强的保证：ICSE 2026 的工作给出面向 LLM agent 的可验证安全工具使用方法，把"哪些调用序列被允许"变成可检查的性质[13]。

**(4) 隔离：执行环境的边界与它的已知裂缝**

- 一篇针对 AI 编码 agent 执行安全研究现状的批评性论文指出，隔离、访问控制、TOCTOU（检查时到使用时）三类机制的研究彼此割裂，导致真实系统里出现"各自都对、组合起来有洞"的问题——尤其是审批时看到的动作与实际执行的动作之间存在时间窗[14]。
- 评测要在"硬化环境"里做：Permission Denied 提出对编码 agent 在加固环境中的**策略分级评测**，衡量 agent 在权限受限时的行为与绕过倾向[15]。
- 越界不只来自攻击，也来自"过度积极"：Overeager Coding Agents 测量了 agent 在**良性任务**上执行范围外动作的比例，说明即使没有攻击者，agent 也会自发扩大作用域[16]。
- 不要依赖黑名单：One Goal, Many Commands 系统性刻画了 agent 场景下**拒绝名单的脆弱性**——同一目标可以由大量等价命令达成，黑名单几乎必然被绕过[17]。这条结论直接否定了"禁几个危险命令就行"的常见做法。

**落地建议**：默认白名单 + 能力租约 + 隔离工作区。具体为：每个任务签发短时效、范围限定的凭证[7][12]；工具调用走策略引擎强制授权而非提示词约束[9][10]；写操作只允许落在隔离工作副本，合并回主干必须经过独立通道；对"审批展示内容 ≠ 实际执行内容"做一致性校验[14]。

### 1.3 环节 C：代码安全（产出物、注入通道、供应链、数据边界）

**(1) 产出物本身的缺陷基线**

- 大规模对比研究显示，AI 生成代码与人类代码在缺陷、漏洞与复杂度分布上存在系统差异，不能默认"生成即合格"[18]。
- 面向真实任务的基准 Is Vibe Coding Safe? 测量了 agent 生成代码的漏洞率，为"是否需要强制安全门禁"提供了量化依据[19]。
- 更贴近治理的是"安全债"视角：一项研究发现自治编码 agent 在**高影响路径**上引入的安全问题增长速度可能超过传统人工评审的处理能力[20]——这解释了为什么"事后评审"这一单一手段不足以兜底。

**(2) 注入通道：agent 的输入面就是攻击面**

- 对 agentic 编码助手的系统性分析覆盖了 skills、工具与协议生态三类载体的提示注入漏洞[21]，是内部安全基线设计的直接参照。
- GitInject 展示了在 AI 驱动的 CI/CD 流水线中真实可行的提示注入攻击[22]。结合前述"agent 会改 CI/CD 配置"的实证[2]，可以看到一条完整的高危链路：仓库内不可信文本 → agent 读取 → 流水线权限被利用。

**(3) 供应链：幻觉依赖是新的入口**

- Importing Phantoms 量化了 LLM 生成不存在包名的现象及其可被抢注利用的风险[23]。企业内部必须在制品层面拦截：依赖必须来自内部镜像源、新依赖引入需人工或策略审批。

**(4) 知识产权与许可合规**

- LiCoEval 面向代码生成场景系统评测了 LLM 的许可证合规能力，发现模型在许可识别与遵从上存在明显缺口[24]。内部治理需要把"生成代码的许可来源"纳入合规检查，而不是只查安全漏洞。

**(5) 数据边界：别让内部源码流出去**

- CodeCloak 针对 LLM 代码助手造成的**代码泄露**问题给出缓解方法[25]。对内部使用而言，这条对应的是"上下文里带走了什么"：仓库片段、密钥、内部架构信息。部署形态（自托管/私有化/网关脱敏）应由数据分级决定。

### 1.4 环节 D：审计追踪（让"发生了什么"可复原）

**(1) 执行层留痕**

- Agent-Sentry 提出用**执行溯源（execution provenance）**来约束 LLM agent，把 agent 的动作与其因果来源绑定，从而能事后复原"哪一步导致了哪个变更"[26]。
- ESAA-Security 给出面向 AI 生成代码安全审计的**事件溯源、可验证**架构，强调审计记录本身要不可篡改、可重放[27]。

**(2) 制品层溯源**

- 自动化、可解释的 AI 生成代码溯源方法，试图回答"这段代码是谁（哪个模型/哪次会话）产生的"[28]。
- 一篇系统性综述梳理了 AI 生成代码的水印与归属方法的能力边界，明确指出当前方法在鲁棒性与实用性上仍有较大差距[29]——这意味着企业不能只依赖检测，必须**在生成时主动记录**。

**(3) 一个容易被忽视的陷阱：agent 自己写的日志不能当审计证据**

- 实证研究比较了 AI 编码 agent 与人类的日志编写行为，发现两者在日志位置、级别与信息量上存在系统差异[30]。推论很直接：**审计能力必须由平台侧强制注入，不能指望 agent 自觉记录**。

**(4) 责任归属的制度侧**

- 一项对 AI 编码工具**服务条款**的分析指出，主流工具的条款普遍把责任推给使用方，学界据此提出了软件工程中"可问责 agent"的研究路线[31]。企业采购与内部规章必须正视这个责任分配现状。
- IUI 2026 的研究考察了 AI 自治程度如何重塑代码的**所有权、责任与披露**认知，发现自治程度越高，开发者对"这是我的代码"的认同越弱，责任归属越模糊[32]。这是"责任真空"的经验证据。
- 开源社区已经在用**贡献规则**这一工具：一项研究分析了贡献指南如何针对 GenAI 增补 AI 政策、披露要求与人在环要求[33]，其条款结构可以直接借鉴到企业内部的提交规范。

**落地建议**：三层留痕——① 会话层（提示、模型版本、工具清单、授权范围）；② 执行层（每次工具调用、参数、结果、审批记录，采用事件溯源且不可篡改[26][27]）；③ 制品层（每个 commit/PR 标注 agent 身份、会话 ID、人工复核人[28][32][33]）。三层之间用同一个会话 ID 串联，保证从"线上事故"能一路回溯到"哪次提示、哪次授权、谁批准的"。

### 1.5 环节 E：人机协作与人工监督

- **监督在实务中如何真的发生**。FAccT 2026 的研究实地考察了开发者监督软件 agent 的具体工作、困难与启发式做法，指出监督是一项有成本、有技巧、会疲劳的实际劳动，而不是一个开关[34]。
- **人工监督的能力上限是可测的，而且不高**。Coding with "Enemy" 直接测试了人类开发者能否发现 agent 的蓄意破坏行为，结果说明单纯依赖人工评审无法可靠拦截精心隐藏的恶意改动[35]。
- **"人工确认"这一环本身会被绕过**。What You Approve Is What Executes 提出黑箱 agent 场景下的**同意完整性**问题：用户批准的内容与实际执行的内容可能不一致[36]。这与前述 TOCTOU 问题呼应[14]，说明审批 UI 必须做"所见即所执行"的强绑定。
- **自治度应当动态可调**。Hedwig 提出让编码 agent 在本地监督下动态调整自治程度的机制[37]，比固定的"全自动/全手动"更贴合真实工程节奏。

**落地建议**：把人工监督当稀缺资源来分配。高风险变更（认证授权、加解密、支付、数据删除、CI/CD 与基础设施）强制人工评审并降低 agent 自治度[37]；低风险变更走自动化门禁 + 抽样复核。同时承认人工评审对隐蔽恶意改动无效[35]，必须靠权限边界与隔离在前置环节兜底。

## 二、落地风险清单：最容易"看起来做了治理但其实没有"的九个坑

1. **防御在真实动态环境里失效**。AgentDyn 专门评估 agent 安全防御在真实动态环境中的**可部署性**，发现实验室里有效的防御在动态环境中大幅退化[38]。内部选型必须做环境贴近的验证，而不是看论文数字。
2. **安全门禁与任务成功率的硬权衡**。The Verifier Tax 量化了工具使用 agent 中"安全—成功率"的权衡，并指出该代价随任务时长增长而放大[39]。治理方案如果不承认这个代价，最终会被业务侧以"太慢"为由绕开。
3. **黑名单式管控必然被绕过**[17]；应转为白名单 + 能力模型 + 隔离[9][10][12]。
4. **审批与执行不一致**。TOCTOU 与同意完整性问题使"点了同意"不等于"执行了同意的内容"[14][36]。
5. **审计日志不可用**。依赖 agent 自行记录会得到不适合审计的日志[30]；溯源必须由平台强制生成[26][27]。
6. **归属检测能力被高估**。水印与归属方法的鲁棒性尚不足以承担事后追责的主要证据责任[29]，必须以生成时主动标注为主[28]。
7. **责任分配悬空**。工具条款把责任转移给使用方[31]，同时高自治削弱开发者的责任认同[32]——若企业不显式规定"署名人即责任人"，就会形成无人负责的灰区。
8. **政策与实践脱节**。对敏捷团队的研究发现，组织层面的 GenAI 政策与团队实际使用之间存在明显落差[40]；只发文件不改工具链等于没治理。
9. **评审容量成为新瓶颈**。产出加速后评审侧拥堵，是企业级落地中被反复观察到的现象[3][1]。治理设计必须同时给出"提高评审吞吐"的手段（自动化门禁、变更粒度限制、风险分流），否则治理会被业务压力冲垮。

此外，两项面向工业界的经验性研究给出了组织侧的建议清单：一是工业软件开发中高效且负责任地采用 LLM 的建议[41]，二是企业环境下 AI 编码助手的使用状况、效果与需求实证[42]，两者都强调"工具能力"之外的组织配套（培训、规范、度量）才是采纳成败的关键。

## 三、一个可直接执行的分阶段落地路线

**阶段一（0–1 个月）：确权与止血**
- 为每个 agent 建立独立身份，接入企业 IAM，禁止共用凭证[7][8]。
- 关闭直接推送主干与直接改 CI/CD 的能力；agent 一律走 PR[2][22]。
- 上强制审计：会话/执行/制品三层留痕由平台注入[26][27][30]。

**阶段二（1–3 个月）：边界与门禁**
- 用 ARC 式风险分级定义三档 agent 权限，白名单化工具集[5][9][10]。
- 在硬化环境中做策略分级评测，检验越界行为与绕过倾向[15][16][17]。
- 建立制品门禁：SAST/依赖来源校验（拦截幻觉依赖）[23]、许可证检查[24]、密钥与源码外泄检测[25]。

**阶段三（3–6 个月）：责任与协作机制**
- 把"AI 参与度披露 + 署名人即责任人"写进提交规范与代码评审规范[32][33][31]。
- 按风险等级分配人工评审资源，高风险强制人工 + 降低自治度[34][35][37]。
- 建立监督成本与评审吞吐的度量，防止评审侧成为隐性瓶颈[3]。

**阶段四（持续）：验证与迭代**
- 定期在贴近生产的动态环境中回归验证防御有效性[38]。
- 显式跟踪"安全门禁带来的成功率损失"，用数据调节严格度而非拍脑袋[39]。
- 定期核对政策文本与团队实际行为的偏差[40][41][42]。

## 四、证据强度与空白说明

- **证据最扎实的部分**：权限边界与隔离（有大量可复现的机制研究与基准[9][10][11][13][15][16][17]）、AI 生成代码的缺陷与漏洞基线（多个大规模实证[18][19][20]）、agent PR 的工程后果（MSR/TOSEM 系列实证[1][2]）。
- **证据中等的部分**：审计与溯源（架构提案多、跨组织的长期落地评估少[26][27][28]），归属与水印方法的可靠性已被系统性质疑[29]。
- **证据最薄弱的部分**：责任追究的法律与制度侧。目前主要是条款分析与认知研究[31][32]，缺少针对"企业内部 agent 造成生产事故后如何定责"的判例级或多组织实证；企业治理设计在这一块只能靠内部规章先行明确。
- **方法论提醒**：该领域 2026 年新增文献量极大且以预印本为主，很多机制类工作尚未经过独立复现，选型时应优先采用有第三方评测或已进入 ICSE/FSE/MSR/TOSEM 等场域的成果[11][13][1][2][34]。
