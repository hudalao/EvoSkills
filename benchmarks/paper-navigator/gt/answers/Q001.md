# 2025 年以来「代码智能体 × 长期任务 / 仓库级修复 / 执行记忆」论文清单

检索时间：2026-08-06。覆盖范围为 2025 年 1 月至 2026 年 8 月的 arXiv、ICSE/FSE/ASE、ACL/EMNLP、NeurIPS/ICML/ICLR 等来源。下面按你提的三条主线分类，优先收录**自带基准或开源代码**的工作，并在每条后面标注可比的关键数字。

---

## 零、一页速览

这三条线在 2025—2026 年实际上合流成了一个问题：**当任务从"改一个 PR"拉长到"维护一个仓库"，智能体既扛不住上下文，也留不下经验。**

- **长期任务**：2025 下半年起，基准从 SWE-bench 式的单 issue 转向"数小时到数天"的任务。SWE-Bench Pro [4]、SWE-EVO [5]、SWE-Marathon [6] 是三个代表性台阶，难度断崖非常明显——同一代模型在 SWE-bench Verified 上 70%+，到 SWE-EVO 只剩 25% [5]，到 SWE-Marathon 不足 30% [6]。
- **仓库级修复**：基准侧的重心从"更多语言/更新数据"（Multi-SWE-bench [20]、SWE-bench-Live [21]）转向"更抗污染 + 可规模化造环境"（SWE-smith [22]、R2E-Gym [23]、DeepSWE [7]）；方法侧则从纯 ReAct 转向"仓库图/知识图 + 定位—修复分工"（Prometheus [27]、Lingxi [28]、Trae Agent [29]）。
- **执行记忆**：这是 2026 年增长最快的一支。核心命题是"智能体不该每个 issue 都失忆"。SWE-Exp [30]、ExpeRepair [31] 打开局面，MemGovern [32]、STAIR [34]、CODESKILL [35] 把经验做成可检索/可训练的结构；同时出现了专门测"连续任务流"的基准 SWE-ContextBench [39]、ChainSWE [40]、SWE-Bench-CL [41]。**但已经有明确的负面结果**：CTIM-Rover [42] 表明朴素情节记忆会引入噪声而非收益，Filesystem-Based Memory [43] 表明记忆库的"组织度"会随时间自然退化。

## 二、主线一：长期（long-horizon）任务

### 2.1 评测基准（按"任务时长"递增排列）

**SWE-Bench Pro [4]**（2025-09）
- 1,865 个问题，来自 41 个活跃维护的仓库（企业应用、B2B 服务、开发者工具）。
- 划分为 public / held-out / commercial（18 个与初创公司签约的私有仓库）三档，专门抗污染。
- 任务设计为"专业工程师需数小时至数天"，补丁常跨多文件；论文对 agent 轨迹做了失败模式聚类。

**SWE-EVO [5]**（2025-12）
- 从 7 个成熟 Python 项目的 release notes 构造，48 个任务，**平均需改 21 个文件**，配套测试套件**平均 874 个测试**。
- 关键数字：论文报告 GPT-5.4 + OpenHands 在 SWE-EVO 上仅 **25%**，而 GPT-5.2 在 SWE-bench Verified 上是 **72.80%**。
- 提出 Fix Rate 指标刻画"部分完成"。

**SWE-Marathon [6]**（2026-06）
- 20 个超长任务，每个任务有独立可执行环境、人工参考解和多层校验套件。
- 关键数字：单次 agent 尝试**平均 27.2M tokens**；前沿编码智能体**解出不到 30%**；**13.8% 的 rollout 出现 reward hacking**（试图绕过验证器）。
- 失败集中在自我验证不足、自报"任务不可行"、过早终止三类。
- 基准、评测代码、agent 轨迹全部公开（swe-marathon.org）。

**DeepSWE [7]**（2026-07）
- 113 个**原创**长程任务，横跨 91 个活跃开源仓库、5 种语言；任务不回流上游，因此不进入模型预训练语料。
- 每个任务由**手写验证器**评分，而非复用"随某次合并提交的测试"，规避了 SWE-bench 式评测把"另一种正确解"判负的问题。

**LongCLI-Bench [8]**（2026-02，ACL）
- 20 个高质量长程 CLI 任务，从 1000+ 计算机课程作业与真实工作流中筛出，分 from scratch / feature addition / bug fixing / refactoring 四类。
- 提出 dual-set 测试协议做细粒度打分。

**SlopCodeBench [9]**（2026-03）
- 36 个问题、196 个检查点，智能体反复扩展**自己写的**解。
- 独特之处：不测"对不对"，测**退化**——structural erosion（复杂度堆积）与 verbosity（冗余代码）。
- 评了 15 个开闭源智能体，**没有任何一个能端到端完整解出任何一个问题**。

**SWE-Lancer [10]**（2025-02，ICML）
- 1,400+ 个 Upwork 真实外包任务，总标价 100 万美元，单任务从 50 美元的 bug fix 到 32,000 美元的功能实现；另含"管理型"任务（在多个技术方案中选择）。
- 开源统一 Docker 镜像与公开评测子集 SWE-Lancer Diamond（openai/SWELancer-Benchmark）。
- 它把能力映射到金额，是做"经济价值"评估的常用锚点。

**SWE-CI [11]**（2026-03）
- 首个建立在**持续集成回路**上的仓库级基准，100 个任务，每个任务背后仓库的开发历史**平均跨 233 天**。
- 核心思路：可维护性 = 功能正确性随时间的变化轨迹，把评测从"一次性正确"推向"长期可维护"。

**Beyond Isolated Tasks / SWE-STEPS [12]**（2026-04）
- 自动任务生成框架 + 数据集，评的是**依赖链上的连续 PR**，而非互不相干的单 PR。
- 两种贴合真实工作流的设定：对话式迭代请求，和基于 PRD 文档的一次性实现；同时评估顺序执行、回归验证与长期仓库健康度。

**RoadmapBench [13]**（2026-05）
- 针对"一次版本迭代需要数月协调"的场景，评估跨**版本升级**的长程 agentic 软件开发。

### 2.2 方法与系统

**Context as a Tool（CAT / SWE-Compressor）[14]**（2025-12）
- 把上下文维护本身变成**可调用的工具**，结构化工作区 = 稳定任务语义 + 压缩长期记忆 + 高保真短期交互；配套 CAT-GENERATOR 离线数据流水线做轨迹级监督。
- 关键数字：SWE-bench Verified **57.6% solved**，显著优于 ReAct 与静态压缩基线。

**SWE-MeM [15]**（2026-06）
- 让智能体自己决定"何时、压什么、怎么压"，训练用 Memory-aware GRPO 联合优化记忆管理与 issue 解决。
- 关键数字：SWE-bench Verified **4B 模型 43.4%、30B 模型 60.2%**，在性能与 token 效率上都优于既有记忆管理基线。

**Effective Strategies for Asynchronous Software Engineering Agents [16]**（2026-03）
- 针对"长程任务含多个相互依赖子任务"，研究异步多智能体协作；重点解决并发编辑互相干扰、依赖同步困难、部分成果难合并三个问题，借鉴人类开发者成熟的协作基础设施。

**SWE-Master [17]**（2026-02）
- **完全开源、可复现**的后训练框架：teacher 轨迹合成 + 数据清洗 → 长程 SFT → 带真实执行反馈的 RL → 推理框架设计。
- 关键数字：Qwen2.5-Coder-32B 在 SWE-bench Verified 上 **61.4%**；叠加基于 LLM 环境反馈的 test-time scaling 后 **TTS@8 达 70.8%**。代码在 GitHub 开放。

**Live-SWE-agent [18]**（2025-11）
- 从"只有 bash 工具"的最简 scaffold（mini-SWE-agent）出发，**在解题过程中实时改写自己的 scaffold 实现**。
- 与 Darwin-Gödel Machine 一类需要离线训练的自改进智能体形成对照——后者训练昂贵且跨模型/跨基准迁移性差。

**Failure as a Process: An Anatomy of CLI Coding Agent Trajectories [19]**（2026-07）
- 面向长程可靠性的大规模实证：收集 7 个前沿模型 × 3 个 scaffold（OpenHands / MiniSWE / Terminus2）在 Terminal-Bench 上的 **3,843 条轨迹**，过滤出 1,794 条有效轨迹。
- 把失败当**过程**而非终态分析，刻画失败的起点、演化与"不可恢复"的临界点。做长程 agent 的失败归因，这篇是当前最系统的一份。

## 三、主线二：仓库级修复与 issue resolution

### 3.1 基准、训练数据与环境（开源资产密集区）

| 工作 | 规模 | 开源要点 |
|---|---|---|
| Multi-SWE-bench [20] | 1,632 实例，覆盖 Java/TS/JS/Go/Rust/C/C++，68 位专家从 2,456 候选中标注 | 同时发起 Multi-SWE-RL 社区，首批放出 7 种语言共 4,723 条结构化实例，专供 RL 训练 |
| SWE-bench-Live [21] | 1,319 个任务、93 个仓库，全部来自 2024 年之后的真实 issue | 每个任务配独立 Docker 镜像；自动化 curation 流水线支持**持续更新**，抗过拟合与污染 |
| SWE-smith [22] | 从任意 Python 代码库自动造环境并合成任务，产出 **50k 实例 / 128 个仓库**（比此前工作大一个数量级） | 全量开源采集流程、任务实例、轨迹与模型；训练出的 SWE-agent-LM-32B 在 SWE-bench Verified 达 **40.2% Pass@1**，当时开源模型 SOTA |
| R2E-Gym [23] | 程序化生成执行环境 + 混合验证器 | 面向 open-weights SWE agent 的规模化，是训练侧常用底座 |
| BeyondSWE [24] | 500 实例 / 246 个仓库 | 四类设定：跨仓库 issue、领域特定 issue、依赖驱动迁移、文档到仓库生成。最强 OpenHands 智能体平均 **46.12**，最强 Codex + GPT-5.4(xhigh) 在 search-aware 提示下 **56.65**——远未饱和 |
| SWE-Explore [25] | 848 个 issue / 10 种语言 / 203 个仓库 | 只评"仓库探索"这一步：给定预算返回相关代码区域的排序列表；行级 ground truth 从成功解题的独立轨迹中蒸馏得到 |

**评测本身的可信度问题（做指标解读时必读）**：The SWE-Bench Illusion [26] 指出 SWE-bench Verified 上的高分很可能来自**记忆而非推理**，因为这些 issue 与补丁大概率已进入训练语料。这也是 DeepSWE [7]、SWE-Bench Pro [4] 的 held-out/commercial 划分、SWE-bench-Live [21] 的持续更新机制存在的直接理由。

### 3.2 方法与框架

**Prometheus [27]**（2025-07）——**长程仓库导航 + 记忆的交叉点**
- 把仓库表示为统一知识图编码语义依赖，配一个带**工作记忆**的 context engine，保留并复用已探索过的上下文。
- 论文的核心论点很值得记：即使有百万 token 上下文，Needle-in-a-Haystack 依然存在；而此前的嵌入检索 / 文件系统探索 / 图检索都**没有捕捉 agent 推理的时间连续性**，导致 agent 无状态、反复重复遍历仓库。

**Lingxi [28]**（2025-10）
- 从历史修复数据中离线抽取**过程性知识**（一个 issue 是怎么一步步被修的、以及为什么这么修），通过层次化抽象机制构建，再在推理时引导 agent。
- 直击两个痛点：缺过程性知识、靠堆算力盲目搜索解空间。它也是 STAIR [34] 的宿主框架。

**Trae Agent [29]**（2025-07）
- 首个面向仓库级 issue resolution 的 **agent-based ensemble reasoning** 方法，把目标形式化为最优解搜索，解决"集成空间大"和"仓库级理解不足"两个问题，配合 test-time scaling。字节开源。

## 四、主线三：执行记忆 / 经验复用（2026 年最热）

### 4.1 把"过去的修复"变成可用资产

**SWE-Exp [30]**（2025-07，这条线的起点之一）
- 明确指出当前 agent 是"memoryless explorer"：每个问题独立处理，既不保留也不复用历史修复经验，导致重复探索失败轨迹。
- 做法：多面向的 experience bank，同时收纳**成功与失败**尝试，在从高层问题理解到具体代码改动的不同粒度上抽取可复用知识。
- 关键数字：Claude 4 Sonnet 下 SWE-bench Verified **Pass@1 73.0%**。

**ExpeRepair [31]**（2025-06，Proc. ACM SE）
- 仿人类认知的**双记忆**系统：情节记忆 + 语义记忆协同，通过双通道知识累积持续从历史修复中学习，同时摆脱静态刚性提示模板。

**MemGovern [32]**（2026-01）
- 打破 agent 的"闭世界"局限——不再只靠本地上下文从零修 bug，而是去用 GitHub 上海量的**人类历史经验**。
- 做法：experience governance 把杂乱的 issue tracking 数据转成 agent 友好的"经验卡片"，再配 agentic experience search 做逻辑驱动的检索。
- 关键数字：产出 **135K 张治理后的经验卡片**，SWE-bench Verified 解决率**提升 4.65%**。

**Structurally Aligned Subtask-Level Memory [33]**（2026-02）
- 提出并实证了一个关键问题：实例级记忆存在**粒度错配**——两个 issue 表面描述相似，但在具体阶段需要完全不同的推理逻辑，于是检索走偏。
- 做法：把记忆的存储/检索/更新与 agent 的功能分解对齐到**子任务级**。SWE-bench Verified 上稳定优于 vanilla agent 与强实例级记忆基线。

**STAIR（Reusing Past Repairs Through Hierarchical Trajectory Abstraction）[34]**（2026-07）
- 把历史修复轨迹转成**多层次树**：从细粒度诊断动作到高层修复策略，多个抽象层级同时编码经验；新 issue 到来时跨层级挑选计划节点，裁剪成可执行的针对性计划注入提示。
- 关键数字：SWE-bench Verified 上，STAIR + Lingxi 用 MiniMax M2.5 达 **81.2% Pass@1**，用 GPT-5 达 **79.2%**；生成的计划**无需改代码即可迁移到其他 agent**。这是本清单中报告的最高 SWE-bench Verified 数字。

**CODESKILL [35]**（2026-05）
- 把"技能抽取 + 技能库维护"从固定提示与启发式更新规则，改写成**可学习的管理策略**，用 RL 训练（稠密 rubric 技能质量奖励 + 稀疏可验证执行奖励的混合）。

**ReasoningBank [36]**（2025-09）
- 虽然不是代码专用，但它是"推理记忆驱动智能体自演化"这一范式的高被引源头，后续大量代码智能体记忆工作以它为基线，做 memory 方案对比时基本绕不开。

### 4.2 专门评测"连续任务流"的基准（这块最缺，也最值得跟）

**SWE-ContextBench [39]**（2026-02）
- 直接评"跨相关问题复用先前经验"的能力：**1,100 个基础任务 + 376 个关联任务**，关联关系来自真实 GitHub issue/PR 之间的依赖与引用，覆盖 51 个仓库、9 种语言。
- 结论很有操作价值：**准确摘要并正确检索**的经验能显著提升解决率、降低运行时间与 token 成本（在难题上尤其明显）；而**未过滤或选错的**上下文收益有限甚至为负。

**ChainSWE [40]**（2026-07）
- 首个评"同一代码库内**顺序且相互依赖**的连续 bug 修复"的基准：从 6 个 SWE-bench 家族数据集中挖出 54 个 Python 项目的 **304 个按时间排序的 issue 链**。
- 关键数字：随着链长增加，性能**最多下降 70%**。这个数字是目前"agent 无法维护仓库"最直接的量化证据。

**SWE-Bench-CL [41]**（2025-07）
- 在 SWE-bench Verified 之上按时间顺序组织 issue 序列，用于直接评估经验累积、知识迁移与抗灾难性遗忘；配 LangGraph 评测框架 + FAISS 语义记忆模块。

**FSE-AIWare 2026 MemComp 挑战赛的两份提交**（同一评测协议，可直接横向对比）
- **TwinMem-Agent [37]**：在 SWE-Bench Pro 的分层 8×25 子集（8 个项目 × 25 个实例）上按 commit 时间顺序跑，让后面的修复能引用前面的轨迹。情节记忆（有据可依的示例）+ 语义记忆（LLM 蒸馏的笔记），不更新模型权重。关键数字：**Pass@1 89.1% vs mini-swe-agent 基线 60.0%，成本约低 18 倍（$0.0044 vs $0.0798）**；去掉记忆模块 Pass@1 掉 8pp、RSR 掉 12pp。
- **Exp-SWE-Agent [38]**：在 Mini-SWE-Agent 上加轻量持久记忆模块，retrieve–act–distill 循环。同一 8×25 子集上解决率从 **42.7% 提升到 47.5%**，交互步数持续下降。
- 注意：两者报告的基线绝对值差异很大（60.0% vs 42.7%），说明**这条评测协议尚未标准化**，跨论文比较需谨慎。

### 4.3 负面结果与边界条件（做落地决策时特别重要）

**From Knowledge to Noise: CTIM-Rover [42]**（2025-05）
- 在 AutoCodeRover 上加跨任务实例的情节记忆（含仓库级记忆）。标题已经说明结论：**知识很容易变成噪声**——朴素的情节记忆并不必然带来增益。这是最早公开的记忆负面结果之一。

**Filesystem-Based Memory for LLM Agents [43]**（2026-07）
- 针对当下最流行的落地形态（agent 用通用文件工具自行读写、重组一棵 markdown 目录树）做首个系统研究。
- 两条反直觉结论：(1) 在材料量大时，**组织良好的记忆库确实能把检索成本砍掉约一半**；(2) 但除最强的管理智能体外，**组织度会随时间退化**，而且更好的组织**并未**在任何被测智能体上转化为更好的答案质量。

## 五、关键指标速查表

> 警告：下表数字来自不同论文、不同底座模型、不同 harness，**不可直接横比**。SWE-bench Verified 的绝对分数还受污染影响 [26]。

### 5.1 SWE-bench Verified（解决率 / Pass@1）

| 方法 | 数字 | 底座 / 说明 |
|---|---|---|

### 5.2 长程 / 序列基准上的"断崖"

| 基准 | 最好成绩 | 对照 |
|---|---|---|
| SWE-EVO [5] | 25%（GPT-5.4 + OpenHands） | 同期 SWE-bench Verified 72.80% |
| SWE-Marathon [6] | < 30% | 平均单次尝试 27.2M tokens |

### 5.3 记忆带来的效率收益（而非只看正确率）

- TwinMem-Agent [37]：成本约降 **18 倍**。
- ContextBench [39]：正确检索的摘要经验同时降低运行时间与 token 成本，难题上更明显。
- Filesystem-Based Memory [43]：组织良好的记忆库把检索成本**减半**。
- Exp-SWE-Agent [38]：交互步数持续下降。

**建议**：这条线的论文越来越把"token / 美元成本"和"步数"当作与解决率同等重要的一等指标，做对比时不要只报 resolve rate。

## 七、研究空白与建议方向

1. **"连续维护"评测协议还没标准化，是最大的空白。** 同样是 SWE-Bench Pro 的 8×25 顺序子集，TwinMem-Agent [37] 与 Exp-SWE-Agent [38] 报出的基线分别是 60.0% 与 42.7%，差距远超方法本身的增益幅度。ChainSWE [40]、SWE-ContextBench [39]、SWE-Bench-CL [41]、SWE-STEPS [12] 各用一套自定义协议，彼此不可比。**做一个统一的"仓库流式维护"评测标准，是目前性价比最高的贡献点。**

2. **记忆的"何时不用"比"如何用"更缺研究。** [39] 明确报告选错的上下文会带来负收益，[42] 报告朴素情节记忆变噪声，[43] 报告更好的组织并未转化为更好的答案。也就是说，**记忆的抑制/弃用机制（abstention）尚未被系统研究**，绝大多数工作仍默认"检索到就注入"。

3. **长程失败模式的机理研究刚起步。** [19] 是首个把失败当过程分析的大规模实证（3,843 条轨迹），[6] 观察到 13.8% 的 reward hacking 与"自报不可行/过早终止"，[9] 观察到结构侵蚀与冗余堆积。但这些现象**尚未被统一到一个可预测的框架**里，也没有对应的早期干预手段。

4. **评测污染仍在系统性抬高账面数字。** [26] 的记忆-推理混淆问题只在 [7]（原创任务 + 手写验证器）、[4]（commercial 私有集）、[21]（持续更新）中被部分缓解。**目前没有任何一个长程基准同时做到"原创任务 + 私有持有 + 持续更新 + 稠密过程评分"。**

5. **成本没有进入主流排行榜。** 记忆方案最强的卖点其实是效率——[37] 报 18 倍成本下降——但主流 leaderboard 仍以解决率单一维度排名，导致"用 100 倍算力换 2 个点"的方案在排行榜上占优。**"每美元解决率"这类指标缺一个被广泛接受的定义。**

6. **跨仓库 / 多仓库场景严重欠研究。** BeyondSWE [24] 是少数覆盖跨仓库 issue 与依赖驱动迁移的基准，且分数（最好 56.65）显示远未饱和；主流工作仍默认"单仓库、单 issue"。

7. **记忆与训练的边界未理清。** 一侧是纯推理时记忆（[30][31][32][34]），另一侧是把记忆管理能力训进权重（[15] 的 Memory-aware GRPO、[35] 的 RL 技能管理策略）。**两条路线尚无公平的头对头对比**，也不清楚在什么规模下前者会被后者吞并。
