# 企业知识库里 RAG、长上下文与 agent memory 的分工与路线选择

## 零、结论先行

这三者不是互相替代的三个候选方案，而是**三个不同层次的部件**：RAG 管"组织有什么知识"，长上下文管"这一次任务要看哪些材料、看多深"，agent memory 管"这个用户/这条业务线跨会话累积了什么状态"。近年把 RAG、记忆系统、工具调用统一归入"上下文工程"的综述，正是把它们当作同一套上下文供给流水线里的不同组件来组织的[1]。

权限治理不是"第四条路线"，而是横切这三层的准入条件：企业知识库和公开语料最大的差别就是每条知识都带主体、带密级、带有效期，而现有研究里绝大多数 RAG 工作默认"检索到的内容对任何用户同等可见"[20]。因此正确的落地顺序是**先定权限模型，再选技术路线**，而不是反过来。

下面按"分工 → 证据 → 场景选型 → 组合架构 → 风险点"展开。

---

## 一、三条路线各自解决什么问题（分工定位）

| 维度 | RAG | 长上下文 | agent memory |
|---|---|---|---|
| 主要解决 | 语料规模远超窗口；知识要可增删改 | 单次任务的整体理解、跨段落推理 | 跨会话的状态、偏好、经验累积 |
| 知识来源 | 组织共享的权威文档 | 本次任务临时装载的材料 | 交互过程中自己写出来的条目 |
| 天然特性 | 知识量大、静态、多主体 | 一次性、可丢弃 | 从零开始、随交互增长[14] |
| 权限颗粒 | 文档/字段级，可直接对接 IAM[20] | 装载即授权，窗口内无隔离 | 按主体分区，且写入即长期留存 |
| 主要成本 | 索引与检索工程 | token 与延迟 | 记忆维护（抽取/更新/合并）开销[16] |
| 可审计性 | 强（可给出引用、可撤回） | 中（证据在提示里但不落库） | 弱（结论来自被改写过的记忆） |

一个容易被忽略的关键区分：**RAG 和 memory 表面上都是"检索 + 拼接"，但 memory 系统是从零开始、随对话逐步增长的**，这个特性使得在语料还很小的时候，那些对传统 RAG 不现实的朴素做法（全量装载、穷尽搜索、完整重排）反而是最优解[14]。这一点直接决定了小规模场景不该过早上记忆基础设施。

## 二、四类证据的对比

### 2.1 RAG 与长上下文：谁在什么条件下更好

- **资源充足时长上下文平均更强，但 RAG 便宜得多。** 在多个公开数据集、三个前沿模型上的系统对比表明：算力和上下文预算给足时，长上下文（LC）的平均表现持续优于 RAG；但 RAG 显著更低的成本仍是其明确优势。据此提出的 Self-Route 让模型自反思后把查询路由到 RAG 或 LC，在保持接近 LC 表现的同时大幅降低计算成本[2]。
- **但不存在普适的路由规则。** LaRA 用 2326 个测试用例、4 类实用 QA 任务、3 类自然长文本评测了 7 个开源和 4 个闭源模型，结论是最优选择取决于模型参数规模、长文本能力、上下文长度、任务类型以及检索片段特性之间的复杂交互——"没有银弹"[3]。这意味着任何"我们统一走 X 路线"的一刀切决策都会在部分场景上付出代价。
- **长上下文确实能在一定范围内吞掉检索。** LOFT 用需要百万 token 级上下文的真实任务证明，长上下文模型在从未针对检索训练的前提下，能与最先进的检索与 RAG 系统打平[4]。这是"少量长文档场景可以不建索引"的直接依据。
- **任务类型决定胜负方向。** 在过滤掉"无需外部上下文即可回答"的问题、并采用更强检索方法后的复评显示：LC 在 QA 类（尤其是百科式问题）上普遍占优；摘要式检索接近 LC，而分块式检索明显落后；但在**对话式查询和泛化查询**上 RAG 反而有优势[5]。企业知识库里大量场景恰恰是对话式的多轮追问。
- **成本锚点。** 更早的对照实验给出了一个仍然实用的量级参考：4K 窗口 + 简单检索增强，可以达到与经位置插值微调到 16K 窗口的模型相当的表现，而计算量小得多；且检索对长上下文模型同样有增益[6]（ICLR 2024）。
- **"多塞点检索结果"会反噬。** 对长上下文 RAG 的实证发现：随着召回条数增加，输出质量先升后降，主要元凶是被检索进来的 hard negative（形似而实非的干扰片段）[7]。企业语料里近重复文档、历史版本、跨部门同名制度极多，这个反转点会来得比公开语料更早。

### 2.2 长上下文的能力边界：不能只看标称窗口

- **有效上下文远小于标称上下文。** RULER 在 17 个长上下文模型、13 类任务上发现，尽管这些模型都声称支持 32K 及以上，但只有一半能在 32K 长度上维持令人满意的表现[8]。
- **去掉字面匹配后退化更剧烈。** NoLiMa 把"针"和问题之间的词面重叠降到最低、迫使模型推断潜在关联，结果 13 个声称支持 128K+ 的模型中，在 32K 处有 11 个跌破其短上下文基线的一半；即便是表现最好的 GPT-4o 也从接近满分的 99.3% 降到 69.7%[9]。企业知识库里用户提问的措辞和文档措辞几乎从不一致，这正是 NoLiMa 所刻画的困难设置。
- **哪怕"检索是完美的"，长度本身仍然伤害表现。** 在数学、问答、代码任务上对 5 个开源与闭源模型的系统实验显示：即使模型能完美检索到全部相关信息，随着输入变长（且仍在其声称长度内），表现仍下降 13.9%–85%；把无关 token 换成空白、甚至掩蔽到只让模型关注相关 token，退化依然发生[10]。这直接否定了"窗口够大就把整个知识库塞进去"的思路。

### 2.3 agent memory：它解决的不是"文档太多"，而是"交互太久"

- **长上下文模型在持续交互上会明显掉链子。** LongMemEval 针对信息抽取、多会话推理、时序推理、知识更新、拒答五项长期记忆能力设计评测，商用聊天助手和长上下文模型在跨持续交互记忆信息上出现约 30% 的准确率下降[11]。
- **专用记忆架构相对全上下文的收益主要在成本，不只是准确率。** Mem0 在 LOCOMO 上对照六类基线（已有记忆增强系统、不同 chunk 和 k 值的 RAG、全上下文、开源记忆方案、闭源模型系统、专用记忆平台），在 LLM-as-a-Judge 指标上相对提升 26%，更关键的是相较全上下文方案把 p95 延迟降低 91%、token 成本节省超过 90%[12]。企业侧的采购决策往往取决于后者。
- **记忆能力必须拆成四项分别验收。** MemoryAgentBench 依据记忆科学把记忆智能体的核心能力拆为精确检索、测试时学习、长程理解、**选择性遗忘**四项，并指出现有方法没有一个能同时掌握全部四项[13]。"选择性遗忘"这一项在企业里直接对应离职、调岗、项目解密等治理需求。
- **规模阈值是可操作的选型判据。** Convomem 用 75336 个 QA 对给出了明确的转折点：**前 30 轮对话长上下文明显最优，到约 150 轮仍可用（有可接受的取舍），超过之后因成本和延迟才需要转向混合或 RAG 方案**；在 150 轮以下的会话历史上，简单全上下文即便在最难的多消息证据场景也能达到 70–82% 准确率，而 Mem0 这类成熟 RAG 式记忆系统只有 30–45%[14]。
- **记忆与检索可以互补而非二选一。** MemoRAG 用一个轻量长程系统先对长上下文构建"全局记忆"、生成草稿答案作为线索，再驱动检索定位证据，专门覆盖传统 RAG 失效的两类前提——查询表述不明确、知识非结构化[15]。这是把 memory 用作"索引层之上的语义导航"而非"另一个知识库"的范式。

### 2.4 权限治理：三条路线各自的失效方式

- **RAG 在企业里最典型的安全事故是"混淆代理"。** ConfusedPilot 针对 Microsoft 365 Copilot 一类的企业 RAG 系统给出了一组漏洞：把恶意文本嵌入被检索文档从而污染回答（完整性破坏），以及利用检索链路的**缓存机制**泄露机密数据（机密性破坏）[18]。注意第二类风险与检索质量无关，纯粹来自工程链路。
- **靠模型自觉守边界是不成立的。** 对"微调 + RAG"组合的企业助手的数据外泄实验表明，在缺乏访问控制强制执行的前提下攻击者可以拿到敏感信息；而提示词净化、输出过滤、系统隔离、训练期隐私机制等既有防御**本质上都是概率性的**，无法提供确定性保证[19]。
- **权限必须下沉到检索层，且异构授权模型合并本身就是风险源。** Permission-Aware RAG 直接对接各数据源自身的 IAM 系统做实时权限校验、执行资源级访问控制，并指出把 RBAC 与 ABAC 这类异构授权模型强行合并，往往带来沉重的合规负担和意外的数据暴露[20]。
- **向量库层面存在"权限正确性 / 召回率 / 延迟"的三角张力。** 向量数据库混合了结构化与非结构化属性、返回的是近似语义结果，这让细粒度访问控制（FGAC）难以实现；在正确执行策略、维持高 ANN 召回、保持低查询延迟三者之间存在固有张力[21]。换言之，"加个权限过滤"在企业规模上不是免费的。
- **RAG 的隐私影响是双向的。** 实证研究显示 RAG 系统会泄露其私有检索库的内容，但同时又能抑制底座模型训练数据的泄露[22]。这提示了一个重要的治理取向：**把敏感知识放在可控的外部检索库里，好过把它固化进模型权重**。
- **记忆层是新增的攻击面。** MEXTRA 在黑盒设置下通过设计攻击提示，从智能体记忆模块中抽取私有的用户-智能体交互记录[23]。更严重的是 FragFuse：攻击者把会触发访问控制的违规内容**拆成碎片、分散写入长期记忆**，之后通过检索重组，最终查询里从不显式出现违规内容——在四类智能体设置、三种主流访问控制机制上平均绕过成功率 86.3%，端到端有害任务成功率 41.1%，且现有提示注入检测器和困惑度检测器都无效[24]。这说明**长期记忆给访问控制引入了一条时间通道**，单次请求粒度的鉴权在有记忆的系统里是不够的。
- **"删除"不等于"合规"。** 保密义务约束的是"不得陈述某个命题"，而部署中的 RAG 系统只能做记录级处置（删文档、改 ACL）。审计框架 Forgetting-by-Design 用撤销前后配对的系统状态做探针，把合规拆成"检索/引用暴露"和"答案层披露或拒答"两个可观测通道，结果显示：**检索层暴露可以被压住，答案层泄露却依然存在**；而降低披露的干预又可能损害合法效用或让引用覆盖率崩塌[25]。
- **动态记忆需要专门的治理架构。** 当记忆从静态检索库演化为动态智能体机制后，出现了记忆污染、语义漂移、隐私脆弱性等新风险；SSGM 框架的做法是把记忆演化与执行解耦，在任何记忆固化之前先执行一致性校验、时间衰减建模和动态访问控制，用以缓解"敏感上下文被固化进长期存储"造成的拓扑性知识泄露，以及"反复摘要导致知识退化"的语义漂移[26]。

## 三、路线选择：什么场景走哪条路

### 3.1 六个判据

先用这六个维度给场景打标签，再对照下面的路线表：

1. **语料体量与更新频率**——是几十份还是几十万份？周更还是日更？
2. **权限颗粒度与主体数量**——全员可见，还是按部门/项目/密级分层？多租户吗？
3. **是否跨会话**——一次性任务，还是要记住上一次谈了什么？
4. **任务性质**——定位事实（extract）还是全局理解/摘要/比对（synthesize）？
5. **成本与延迟预算**——单次问答能承受多少 token 与多长等待？
6. **可审计与可撤回要求**——答案要不要给引用？知识撤销后必须多快、多彻底地失效？

### 3.2 路线对照表

| 场景 | 首选路线 | 依据 |
|---|---|---|
| 全员制度/SOP/产品知识问答：库大、更新频繁、按部门分权、要引用 | **RAG 主线** + 权限下沉到检索层 | 大库超窗口；可增删改可审计；权限必须在检索阶段执行[20][21][29] |
| 单份或少量长文档的深度理解：合同、年报、招标书、事故复盘 | **长上下文主线**，RAG 作兜底 | LC 在资源充足时平均更优[2]；百万 token 级可与检索系统打平[4]；摘要类任务 LC 优势明显[5] |
| 跨系统深搜：文档 + 会议纪要 + 即时消息 + 代码仓 + 工单 | **agentic RAG / deep search**，不是单纯拉长窗口 | 异构多跳企业检索上，最好的 agentic RAG 方法平均分也只有 32.96，瓶颈明确在检索而非生成[30]；企业语料本身横跨九类源、含错归档/近重复/相互冲突的内容[31] |
| 长期助理：记住个人偏好、项目状态、历史决策 | **agent memory** | 长上下文模型在持续交互上掉约 30%[11]；专用记忆把 p95 延迟降 91%、token 成本降 90%+[12] |
| 冷启动 / 会话量还小（< 约 150 轮） | **直接全上下文**，先不上记忆基础设施 | 30 轮以内 LC 明显最优，150 轮内仍可用；此区间简单全上下文 70–82% 对 Mem0 类系统 30–45%[14] |
| 高频重复问答、成本敏感 | **RAG 为主 + 自反思路由** | Self-Route 在保持接近 LC 表现的同时大幅降本[2]；小窗口 + 检索可媲美 4 倍窗口的微调模型[6] |
| 强合规、需要撤回：客户数据、未公开财务、人事、涉密项目 | **RAG（外部可删可审）+ 严格权限**；避免把敏感知识写进长期记忆或微调进权重 | RAG 会抑制训练数据泄露[22]；微调 + RAG 组合下缺乏访问控制会导致外泄，且既有防御是概率性的[19]；记忆一旦固化会带来拓扑性泄露[26] |
| 查询表述模糊、知识非结构化（"帮我看看这个项目当初为什么改方案"） | **memory-augmented retrieval 混合式** | 传统 RAG 依赖显式查询和良构知识两个前提，这类任务上不成立；先建全局记忆生成线索再检索的做法覆盖了这两种失效[15] |

### 3.3 路由本身的注意事项

可以用模型自反思做 RAG/LC 二选一路由[2]，但不要把某一次评测得到的路由规则当成普适规律——最优选择随模型参数规模、长文本能力、上下文长度、任务类型和检索片段特性共同变化[3]。工程上的稳妥做法是把路由阈值做成可配置项，并按业务线定期重测。

## 四、推荐的组合架构（分工怎么落地）

自下而上四层，**上层不得绕过下层**：

1. **治理层（先于一切技术选型）**：统一身份、资源级权限、审计日志、保留与撤回策略。权限校验实时对接各数据源自身的 IAM，而不是在应用侧维护一份影子 ACL[20]。撤回的验收标准不是"文档删了"，而是撤回后的探针测试在检索暴露与答案披露两个通道上都通过[25]。
2. **语料层（RAG 索引）**：权限元数据随分块一起入库；保留版本与时间戳；接受权限过滤会带来召回与延迟代价，并把它纳入容量规划[21]。
3. **会话层（长上下文工作台）**：只装载本次任务精选出的证据，**显式控制长度预算**——因为长度本身就会伤害表现，与检索质量无关[10]，而多召回还会因 hard negative 让质量先升后降[7]。
4. **记忆层（跨会话状态）**：与语料层严格隔离、按主体分区；写入前做一致性校验与访问控制，而不是写入后再补救[26]；把"选择性遗忘"当作一等能力来验收[13]。

这套分层与把 RAG、记忆系统、工具调用统一纳入上下文工程的组件化视角是一致的[1]。

## 五、风险点清单

### 5.1 RAG 路线

- **检索是瓶颈，不是生成。** 异构企业数据上最好的 agentic RAG 方法平均分仅 32.96，失败模式是拿不全证据、在残缺上下文上推理[30]。
- **工程失效点密集。** 对三个不同领域生产系统的经验总结归纳出七类失效点，覆盖内容缺失、排序、整合、格式、特异性等环节[27]；企业落地的额外难点集中在数据安全、准确性、可扩展性和系统集成[28]。
- **企业语料自带噪声。** 错归档、近重复、相互冲突的内容是常态，"识别信息不存在"本身就要作为一类能力去测[31]。
- **可运营的控制点要成体系。** FACTS 框架（Freshness 时效、Architectures 架构、Cost 成本、Testing 测试、Security 安全）与十五个流水线控制点提供了可直接对照的清单，其中明确把"遵守文档访问控制"列为必需环节[29]。
- **安全面：** 检索内容投毒污染回答、检索缓存导致机密泄露[18]；检索库本身可被攻击者反向提取[22]。

### 5.2 长上下文路线

- **标称窗口不可信**：声称 32K+ 的模型只有一半能在 32K 上维持可用表现[8]。
- **词面不重叠时断崖式退化**：13 个 128K+ 模型中 11 个在 32K 处跌破短上下文基线一半[9]。
- **长度本身就是损害**：完美检索、甚至掩蔽掉无关 token 之后，13.9%–85% 的退化仍然发生[10]。
- **多召回反噬**：hard negative 让长上下文 RAG 的质量随召回条数先升后降[7]。
- **成本与权限**：LC 成本显著高于 RAG[2]；且一旦材料装进窗口，窗口内不再有任何隔离——权限判定必须在装载之前完成。

### 5.3 agent memory 路线

- **记忆自身会产生幻觉。** HaluMem 在抽取、更新、问答三个操作阶段上评测，发现现有记忆系统倾向于在**抽取和更新阶段**产生并累积幻觉（编造、错误、冲突、遗漏），随后把错误传播到问答阶段[17]。这意味着端到端问答指标会掩盖真正的故障点。
- **系统级成本常被忽略。** 对智能体记忆的架构与系统双视角分析指出：现有评测规模不足、指标与语义效用不对齐、表现随底座模型大幅波动，而记忆维护带来的延迟与吞吐开销经常被漏算——这是当前记忆系统表现低于理论承诺的直接原因[16]。
- **能力不完整。** 精确检索、测试时学习、长程理解、选择性遗忘四项能力，现有方法没有一个能全部掌握[13]。
- **不要过早投入。** 会话历史在约 150 轮以下时，成熟的 RAG 式记忆系统反而明显不如简单全上下文[14]。
- **隐私与越权：** 记忆模块可被黑盒提示攻击抽取私有交互记录[23]；更棘手的是碎片化写入 + 事后重组的越权路径，对三种主流访问控制机制平均绕过成功率 86.3%，且提示注入检测和困惑度检测都拦不住[24]。
- **语义漂移与固化泄露：** 反复摘要会让知识退化，敏感上下文一旦被固化进长期存储就会形成拓扑性泄露通道，需要在固化前而非之后施加治理[26]。

### 5.4 权限治理层（横切）

- **不要指望概率性防御。** 提示词净化、输出过滤、系统隔离、训练期隐私机制都无法提供确定性保证，访问控制必须做成强制执行[19]。
- **异构授权模型合并本身是风险源。** RBAC 与 ABAC 强行统一容易造成合规负担与意外暴露；更稳妥的做法是对接各数据源自身的 IAM 做实时校验[20]。
- **权限过滤有性能代价。** 在向量库上同时满足策略正确、ANN 高召回、低延迟三者存在固有张力，需要在架构设计期就做取舍[21]。
- **单次请求粒度鉴权不足以覆盖有记忆的系统。** 长期记忆引入了跨请求的时间通道[24]。
- **合规验收要看答案层，不只看数据层。** 删文档、改 ACL 之后系统可能"看起来合规"，答案里却仍然说出已撤销的事实；应当用配对状态探针分别审计检索暴露和答案披露两个通道，并同时监控合规带来的效用损失[25]。

---

## 六、一句话选型口诀

**语料大、要授权、要撤回、要引用 → RAG；材料少、要通读、要综合 → 长上下文；人不变、事在续、要个性化 → agent memory；三者都要先过权限这一关。** 拿不准时，先按 Self-Route 式路由做 A/B[2]，但记住路由规则会随模型和任务漂移，需要定期重测[3]。
