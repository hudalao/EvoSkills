# 检索增强代码生成的源头追溯：API 文档、历史 commit、项目上下文各是从哪几篇开始的

## 零、先给结论

"代码生成里的检索增强"不是一条线，而是三条各自独立起源、后来才在大模型时代合流的线。按你问的三种检索源分别给奠基论文：

| 检索源 | 奠基工作（首篇/最早一批） | 年份 | 一句话贡献 |
|---|---|---|---|
| **项目上下文**（当前正在写的代码 / 同项目其他文件） | CodeBroker [2]；Strathcona [6]；BMN 所在的 Bruch 等 [10] | 2002 / 2005 / 2009 | 首次把"开发者当前编辑状态"自动变成检索 query，去示例库/复用库取回代码来辅助写代码 |
| **历史 commit / 版本历史** | Hipikat [3]；ROSE [4]（与 Ying 等 [5] 同期独立） | 2003 / 2004 | 首次把版本库的 commit 历史当成可检索语料，按当前改动检索"过去一起改过什么" |
| **API 文档** | CodeHow [14]（检索侧）；BIKER [15]；Xu 等 ACL 2020 [21]（生成侧首篇） | 2015 / 2018 / 2020 | 首次把 API 官方文档当作显式外部知识源接进代码检索、再接进神经代码生成 |
| **"检索增强神经代码生成"这一范式本身** | ReCode [16] 与 Retrieve-and-Edit [17]（同年、相互独立） | 2018 | 首次在神经代码生成模型内部显式引用检索回来的已有代码 |

如果只要一个"最早"：**神经代码生成里的检索增强，源头是 2018 年的 ReCode [16] 和 Retrieve-and-Edit [17]**；但它们的思想来源更早，是 2002—2009 年软件工程界的"软件复用推荐系统"一脉 [1][2][3][6][10]。

## 一、时间线（按阶段）

### 阶段 0（1991—2009）软件复用推荐系统：检索增强的史前史

这一阶段还没有"生成模型"，但"用当前上下文去检索、再把检索结果交给开发者补全代码"的完整回路已经成型，后来的 RACG 基本是把最后一步换成了神经生成器。

- **1991 · Cognitive tools for locating and comprehending software objects for reuse** [1]。把"从大型复用库里定位并理解可复用软件对象"正式确立为一个检索 + 认知支持问题，是这条线最早的学术锚点。
- **2002 · CodeBroker** [2]（Ye & Fischer, ICSE 2002）。**项目上下文检索增强的真正首篇**：系统在后台监控开发者在编辑器中的编程活动，从正在写的注释和方法签名里推断"当前任务"，然后**无需开发者发起查询**，主动把复用库中相关的构件推送出来，并根据该开发者已掌握的知识做个性化过滤。论文给出了实证评估，说明这种主动信息投递确实促进了复用。今天所有"IDE 里自动拼上下文去检索"的做法，逻辑与它同构。
- **2003 · Hipikat** [3]（Cubranic & Murphy, ICSE 2003）。**历史 commit 作为检索语料的首篇**：扫描版本控制系统（代码修订/commit）、缺陷库记录、邮件列表与文档，抽出实体与实体间关系，构成项目的"隐式群体记忆"（implicit group memory），再针对新人当前要做的任务从归档里检索并推荐相关制品。该文获 ICSE 2013 最具影响力论文奖，被公认为软件工程推荐系统的开山之作。
- **2004 · ROSE** [4]（Zimmermann 等, ICSE 2004；TSE 2005 扩展版）。**"用 commit 历史指导代码改动"的奠基**：对 CVS 版本历史做关联规则挖掘，得到"过去经常一起被改"的变更模式；开发者改动一处后，ROSE 实时建议"接下来还应该改哪里"。实验设置是在 8 个流行开源项目的真实历史上回放评估，前三条建议中包含正确位置的概率超过 70%。
- **2004 · Predicting source code changes by mining change history** [5]（Ying 等, TSE 2004）。与 ROSE 同期、独立完成的另一条奠基工作，同样从变更历史挖掘关联来预测源码改动。追溯"历史 commit 检索"时这两篇应当并列，不宜只算一篇。
- **2005 · Strathcona** [6]（Holmes & Murphy, ICSE 2005，SIGSOFT Distinguished Paper）。**"自动构造检索 query"的奠基**：从开发者正在写的代码里自动抽取结构上下文（继承了哪个类、调用了哪些方法、实例化了哪些对象），用启发式结构匹配去示例库里找相关示例。关键设计是开发者既不用学查询语言、也不用按特定风格写代码，示例库可以从已有应用直接生成。这正是今天仓库级检索里"用光标处上下文当 query"的原型。
- **2005 · Prospector / Jungloid mining** [7]（Mandelin 等, PLDI 2005）。把"要从类型 A 拿到类型 B 需要哪串 API 调用"形式化为 jungloid 图上的路径搜索，从 API 签名与代码语料里挖掘并合成代码片段。
- **2006 / 2009 · MAPO** [8][9]（Xie & Pei, MSR 2006；Zhong 等, ECOOP 2009）。从开源代码库里挖掘 API 用法模式并按上下文推荐。ECOOP 2009 版的实验设置很值得注意：做的是**人因对照实验**——面对较复杂的 API 用法时，用 MAPO 的程序员写出的代码比用当时两个最好的代码搜索工具的对照组 bug 更少。
- **2009 · Learning from examples to improve code completion systems** [10]（Bruch 等, ESEC/FSE 2009）。**检索增强代码补全的直接祖先**：指出当时 IDE 的补全只依赖静态类型系统、候选按字母序排、与当前上下文无关；于是实现了三种从既有代码库学习的智能补全系统（其中近邻式的示例匹配是核心思路），做了大规模定量评测，把最好的一个集成进 Eclipse 并补做用户研究，证明"从示例库里学/取"的补全显著优于主流补全。

### 阶段 1（2012—2017）统计语言模型 + 项目局部性：把"项目上下文"变成模型的一部分

- **2012 · On the naturalness of software** [11]（Hindle 等, ICSE 2012）。证明代码比自然语言更"自然"（n-gram 可预测性更高），把语言模型正式引入代码补全，是后续一切工作的共同前提。
- **2014 · On the localness of software** [12]（Tu, Su & Devanbu, FSE 2014）。**"用当前文件/当前项目做非参数式增强"的直接源头**：指出源码除"自然性"外还有一条被忽略的性质——**局部性**（localness），人写的程序在局部存在大量可利用的规律；据此提出 **cache language model**，在全局 n-gram 之上叠加一个动态缓存最近见过 token 的局部模型，显著改善代码建议。把"cache"换成"retriever"、把 n-gram 换成 LLM，就是今天的仓库级 RAG。
- **2017 · Are deep neural networks the best choice for modeling source code?** [13]（Hellendoorn & Devanbu, ESEC/FSE 2017）。针对代码"频繁变更、词表大且在变、作用域深度嵌套"的特性，改进缓存模型，提出**多层次局部性的嵌套缓存 n-gram 模型**，在当时能胜过深度模型。这篇提供了一条被后来 RACG 反复引用的强证据：**项目局部信息的价值可能高于把知识塞进参数**。

### 阶段 2（2015—2018）API 文档进入检索回路（还在检索侧，未接生成）

- **2015 · CodeHow** [14]（Lv 等, ASE 2015）。**API 文档作为检索资源的首篇代表**：先用 API 官方文档识别用户 query 可能指向哪些 API，再用扩展布尔模型把"文本相似度"和"潜在 API"一起纳入代码检索排序。工程侧把后端部署为 Azure 服务、前端做成 Visual Studio 扩展。
- **2018 · BIKER** [15]（Huang 等, ASE 2018）。明确提出任务描述与 API 文档之间存在**词汇鸿沟**与**知识鸿沟**：用词向量弥合词汇鸿沟，用 Stack Overflow 帖子弥合知识鸿沟，从而按自然语言任务描述推荐 API。这是"API 文档 + 社区问答"双源检索的定型之作。

### 阶段 3（2018）神经检索增强代码生成正式成立

这一年出现两篇相互独立、几乎同时的开创性工作，构成 RACG 的双源头：

- **2018 · ReCode: Retrieval-Based Neural Code Generation** [16]（Hayati 等, EMNLP 2018）。**代码生成里第一篇显式做检索增强的神经工作**。核心设计：先用基于动态规划的句子相似度检索出与输入意图相似的训练句子；再抽取其对应抽象语法树构建动作序列的 n-gram 子树；解码时**提高会产生这些检索到的子树的动作的概率**。动机是纯生成模型记不住大而复杂的代码结构。实验在两个代码生成任务上把 BLEU 最多提升 2.6。
- **2018 · A Retrieve-and-Edit Framework for Predicting Structured Outputs** [17]（Hashimoto 等, NeurIPS 2018）。提出通用的 **retrieve-and-edit** 范式：先按输入检索一条训练样例，再把它编辑成目标输出。核心贡献是一个计算上可行的检索器学习方法——把输入嵌入成任务相关表示，既不依赖手工设计的相似度度量，也不需要与编辑器联合训练，因此可以叠加在任意基础模型之上。实验设置是一个新的 GitHub Python 自动补全任务加 Hearthstone 卡牌基准，两者上都显著超过普通 seq2seq。

同年另外两篇是重要旁支：**CONCODE** [18] 首次把"类的其余部分（成员变量与方法）"这一 **programmatic context** 形式化成代码生成的条件输入并放出 10 万+ Java 样例的数据集（是条件化而非检索，但定义了后来"项目上下文"的问题形态）；**Aroma** [19] 索引数千个开源项目，接受一段部分代码作为 query，用结构化代码搜索取回包含该片段的方法体，再聚类求交产出可直接使用的推荐。

### 阶段 4（2020—2022）API 文档正式接进生成端

- **2020 · Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks** [20]。"检索增强生成（RAG）"这个名字与通用框架的来源，之后几乎所有 RACG 工作都以它为参照系。
- **2020 · Incorporating External Knowledge through Pre-training for Natural Language to Code Generation** [21]（Xu 等, ACL 2020）。**把 API 官方文档接进神经代码生成的首篇**。动机写得很直白：开发者写代码时会上网查资料。它注入两类外部知识——从 Stack Overflow 自动挖的 NL-code 对，以及**编程语言 API 文档**；做法是数据增强加上**基于检索的数据重采样**（retrieval-based data re-sampling）后再预训练。在 CoNaLa 上把当时 SOTA 的 BLEU 最多提升 2.2 个绝对百分点。注意它的检索发生在训练数据构造阶段，还不是推理时检索。
- **2021 · REDCODER** [22]（Parvez 等, EMNLP Findings 2021）。动机是模拟开发者"回忆自己以前写过的代码或摘要"的行为：从检索库取回相关代码或摘要，作为生成/摘要模型的补充输入。两个特点——扩展了稠密检索用于代码；检索库可以是单模态（只有代码或只有 NL）也可以是双模态（代码-描述对）。在 Java 与 Python 的代码生成与代码摘要两类基准上评测。
- **2022 · ReACC** [23]（Lu 等, ACL 2022）。第一次把术语讲清楚：以往方法只用**内部上下文**（同文件或同项目内的代码），ReACC 主张利用**外部上下文**，模仿人"从相似代码里抄"的行为，用词法复制加语义相似检索，采取"检索器 + 自回归代码语言模型"的分阶段训练，在 CodeXGLUE 的 Python/Java 补全上达到当时 SOTA。
- **2022 · DocPrompting** [24]（Zhou 等, arXiv 2022 / ICLR 2023；早期版本名为 DocCoder）。**推理时检索 API 文档的定义性工作**。问题定义非常明确：公开库持续增长与变化，模型不可能靠训练语料跟上所有 API，因此本质上无法泛化到训练中从未出现的函数和库；而人第一次用一个库时会去翻手册。方法是两步——(1) 按 NL 意图检索相关文档片段，(2) 基于意图 + 检索到的文档生成代码；与编程语言无关、与底层神经模型无关。结果：在 CoNaLa 的执行式评测上把 CodeT5 的 pass@1 提高 2.85 个绝对百分点（相对提升 52%）、pass@10 提高 4.39（相对 30%）；在新构造的 Bash 数据集 tldr 上，CodeT5 与 GPT-Neo1.3B 的精确匹配最多提高 6.9 个绝对百分点。
- **2022 · When Language Model Meets Private Library** [25]（Zan 等, EMNLP Findings 2022）。与 DocPrompting 几乎同期、针对**私有库**：私有库的 API 模型必然没见过，但通常配有详细 API 文档。方案分两个模块——**APIRetriever**（稠密检索，从私有库文档里找出有用 API）与 **APICoder**（用这些 API 生成代码，可直接用现成模型，也可在含 API 信息的代码语料上继续预训练）；两个模块都用公开库数据训练后泛化到私有库，并配套构造了面向私有库的评测基准。

### 阶段 5（2022—2023）项目/仓库上下文在大模型时代的重新定义

- **2022 · Repository-Level Prompt Generation (RLPG)** [26]（Shrivastava 等, arXiv 2022 / ICML 2023）。**仓库级检索增强的首篇代表**：提出用一组 **prompt proposals** 从整个仓库取上下文（import、父类文件等相关文件），学习为每个样例生成专属 prompt；关键约束是**不需要访问 LLM 权重**，因此在只有黑盒 API 的场景也能用。实验用 Google Code archives 的仓库做单行自动补全，由 prompt proposals 构成的 oracle 相对 Codex 有 36% 的相对提升。
- **2022 · CoCoMIC** [27]（Ding 等）。指出代码 LM 只看 in-file 上下文会导致幻觉出不存在的类成员函数、或参数不对的调用；提出联合建模 in-file 与 **project-level cross-file context**，配套 **CCFinder**（基于静态分析）定位并取回最相关的跨文件上下文。给定跨文件上下文时，精确匹配相对提升 33.94%、标识符匹配提升 28.69%。
- **2023 · RepoCoder** [28]（Zhang 等, EMNLP 2023）。把检索与生成做成**迭代**流水线：用上一轮生成的代码去重新检索，如此反复，缓解"query 与目标代码分布不一致"的问题。同时提出 **RepoEval** 基准，覆盖行级、API 调用级、函数体级三种粒度。相对 In-File 基线在所有设置上提升超过 10%，并稳定优于一次性检索增强。这是被后续工作引用最多的仓库级 RACG 基线。
- **2023 · RepoFusion** [29]。把"推理时拼上下文"升级为"训练模型去融合多路仓库上下文"，针对的是模型训练时没见过的私有仓库或在建工程。
- **2023 · RepoBench** [30] 与 **CrossCodeEval** [31]。仓库级评测的两条标准线。RepoBench 拆成 RepoBench-R（检索）、RepoBench-C（补全）、RepoBench-P（端到端流水线）三个互联子任务，支持 Python 与 Java；CrossCodeEval 覆盖 Python/Java/TypeScript/C# 四语言，刻意只保留"不看跨文件上下文就无法正确补全"的样例。

### 阶段 6（2018—2025）历史 commit 这条线在神经时代的接续

- **2018 · NNGen** [32]（Liu 等, ASE 2018）。**"历史 commit 作为检索语料"在神经时代最关键的经验证据**：作者复现分析当时的 NMT 式 commit message 生成，发现 NMT 能生成高质量消息的测试 diff，绝大多数在 token 层面与训练集里的某条或某几条 diff 高度相似；据此提出纯基于最近邻检索的 NNGen——直接检索最相似的历史 commit 并复用其消息——效果反超 NMT。这篇是"检索 vs. 生成"之争在软件工程里最早、最有说服力的一次实证。
- **2018 · Learning to Represent Edits** [33]（Yin 等, arXiv 2018 / ICLR 2019）。提出学习"编辑"的分布式表示：用 neural editor 加 edit encoder 抽出一次编辑的关键信息，并把它**应用到新的输入上**；在自然语言与源码编辑数据上验证。它给"把历史 commit 当作可复用、可迁移的知识"提供了表示层基础。
- **2023 · Grace** [34]（Gupta 等, FSE 2023）。**Generation conditioned on Associated Code Edits**：把"相关的既往关联编辑"作为条件喂给预训练大模型来预测下一处编辑，用生成能力应对编辑的多样性、用历史编辑捕捉潜在的开发者意图；在 codex 与 CodeT5 上做 zero-shot 与微调两种设置的评测。
- **2023 · Coeditor** [35]（Wei 等, arXiv 2023 / ICLR 2024，正式版题为 Leveraging Repo-level Diffs for Code Auto-editing）。**训练语料直接来自 commit 历史**：定义多轮代码自动编辑任务——基于同一代码库内最近的改动来预测某个代码区域该怎么改；用行级 diff 表示代码变更，用静态分析构造大的定制化模型上下文；数据集从 **1650 个开源 Python 项目的 commit 历史**中采集。这是把"历史 commit"完整纳入训练与推理上下文的代表作。
- **2025 · Code Researcher** [36]。第一个面向代码的 deep research agent：针对系统级代码的崩溃修复，围绕代码语义、代码模式以及**庞大的 commit 历史**做多步推理式检索，把相关上下文全部收集齐再生成补丁。代表了 commit 历史检索在 agent 时代的形态。

### 阶段 7（2024—2025）反思、评测与综述

- **2024 · CodeRAG-Bench** [37]。不再默认"检索一定有用"，而是系统追问"**在什么场景下检索真的能帮到代码生成、还剩什么难题**"，构建覆盖基础编程、开放域、仓库级三类任务的统一评测基准与统一检索源。
- **2024 · Repoformer** [38]。指出现有方法**无差别地检索**，导致效率与鲁棒性两方面的问题——很大一部分取回的上下文对代码 LM 无用甚至有害；提出**选择性 RAG**，用自监督训练让代码 LM 自己判断"这次检索会不会提升输出质量"，同一模型既当检索策略又当生成器。
- **2025 · Retrieval-Augmented Code Generation: A Survey with Focus on Repository-Level Approaches** [39]。目前最系统的 RACG 综述，主张不要把 RACG 看成静态的"retrieve-then-generate"流水线，而是 context construction、retrieval optimization、generation、environment interaction 四者耦合演化的过程，并按 retrieval substrate / control regime / evaluation setting 三个维度统一梳理已有方法。

## 二、原始贡献与后续演进关系（谱系）

```
【项目上下文线】
  1991 复用库检索[1]
     └─ 2002 CodeBroker[2] 编辑活动→自动 query，主动推送
          └─ 2005 Strathcona[6] 结构上下文自动抽取为 query
               ├─ 2005 Prospector[7] / 2006,2009 MAPO[8][9] API 用法从语料里挖
               └─ 2009 Bruch 等[10] 从示例库学补全排序（近邻检索）
                    └─ 2012 naturalness[11] → 2014 localness + cache LM[12] → 2017 嵌套缓存[13]
                         └─ 2018 Aroma[19] 结构化代码搜索做推荐 / 2018 CONCODE[18] 上下文条件化
                              └─ 2022 ReACC[23]（内部 vs 外部上下文）
                                   └─ 2022 RLPG[26] → 2022 CoCoMIC[27] → 2023 RepoCoder[28] → 2023 RepoFusion[29]
```

## 三、如果只精读几篇

1. **ReCode [16]** —— 神经代码生成里检索增强的起点，方法层面最干净（检索相似意图 → 抽 AST 动作子树 → 解码时加权）。
2. **Strathcona [6]** —— 想理解"用光标处上下文自动构造 query"这个设计从哪来，读这篇。
3. **ROSE [4]** —— commit 历史检索的奠基，评估方法（在真实项目历史上回放）至今仍是这类工作的模板。
4. **Xu 等 ACL 2020 [21]** 与 **DocPrompting [24]** —— API 文档进入代码生成的两个关键节点：前者在训练侧、后者在推理侧。
5. **RepoCoder [28]** —— 仓库级 RACG 事实上的标准基线，附带的 RepoEval 是后续论文最常用的评测集之一。
6. **NNGen [32]** 与 **Repoformer [38]** —— 两篇"泼冷水"的关键论文：前者证明"简单检索可能就够了"，后者证明"无差别检索是有害的"。

## 四、口径与边界说明（供复核）

- **"最早"的判定口径**：本文对"检索增强"要求满足"以当前编程上下文构造 query → 从外部语料检索 → 检索结果参与代码产出"这一完整回路。按此口径，纯代码搜索（不参与产出）与纯上下文条件化（不做检索，如 CONCODE [18]）被标注为旁支而非源头。
- **优先权核验**：ReCode [16] 的参考文献里，代码方向没有更早的检索增强工作，其直接祖先是机器翻译方向的检索式方法；DocPrompting [24] 的参考文献里，最早的文档相关代码生成工作即为 Xu 等 [21]。两处均已逐条核对，未发现更早的同类论文。
- **两组同年独立工作**不宜只取其一：ReCode [16] 与 Retrieve-and-Edit [17]（2018，代码生成范式）；ROSE [4] 与 Ying 等 [5]（2004，变更历史挖掘）。
- **版本歧义提示**：ROSE [4] 有 ICSE 2004 会议版与 TSE 2005 期刊扩展版；DocPrompting [24] 的早期 arXiv 版本题为 DocCoder，与 ICLR 版共用同一 arXiv 编号；Coeditor [35] 的 arXiv 版副标题为 "Leveraging Contextual Changes"，ICLR 2024 正式版改为 "Leveraging Repo-level Diffs"；MAPO 有 MSR 2006 短文 [8] 与 ECOOP 2009 完整版 [9]。追溯时按最早发表年计。
