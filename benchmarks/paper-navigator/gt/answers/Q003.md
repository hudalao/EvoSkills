# LLM agentic 调试/修复 vs 静态分析、测试生成等传统方法：方法对比、适用条件与真实项目评测证据

## 零、一句话结论

近五年的实证结果并不支持"agentic 全面碾压老方法"这个说法。**agentic debugging 的真正增量在于任务边界**——它把"给定缺陷位置、修一个函数"扩展成"给一个 issue、在整个仓库里定位—复现—改—验证"，这是模板式 APR、静态分析修复、传统测试生成从设计上就做不到的 [1][2][4][42]；**但在各自的老地盘上，老方法依然更准、更便宜、更可控**：特定类别的静态告警修复（空指针、SonarQube 规则）由静态分析驱动的方案在真实项目上给出 65%–77% 的命中率并已在 Facebook/Microsoft 生产线上跑了多年 [15][16][17][18][19]，覆盖率导向的测试生成上 LLM 至今仍落后于搜索式与符号执行 [22]。真实项目评测是有的，而且质量最高的几份来自工业界（Google、Meta 规模的内部代码库、Bloomberg、OSS-Fuzz）[31][32][33][34][35][39]，它们给出的数字比公开榜单低得多：企业内部人报缺陷的语义正确率约 18%，生产环境落地率约 25% [31][34]。同时，SWE-bench 家族的效度问题（解法泄漏、弱测试、记忆化）已被多份研究量化，公开分数存在系统性虚高 [47][48][49]。

## 一、方法族总览对比表

表中"代表指标"一律标注评测集，跨行数字**不可直接比较**（评测集、定位假设、成本口径都不同），横向解读方法见第六节。

| 方法族 | 代表工作 | 输入与前提 | 代表指标（评测集） | 成本/延迟 | 适用条件 | 主要局限 |
|---|---|---|---|---|---|---|
| **A. Agentic 修复/调试**（LLM agent 自主用工具、跑测试、迭代） | SWE-agent [1]、AutoCodeRover [2]、RepairAgent [3]、企业内部 Engineering Agent [34] | 自然语言 issue 或失败测试 + 可执行仓库环境 | SWE-bench 全集 pass@1 12.5% [1]；SWE-bench-lite 19% [2]；Defects4J 自主修复 164 个缺陷、其中 39 个此前技术未修 [3] | AutoCodeRover 约 4 分钟/issue（人类同批 issue 平均 2.68 天）[2]；RepairAgent 约 27 万 token≈0.14 美元/缺陷 [3] | 缺陷位置未知、跨文件跨函数、需要读日志/跑测试才能判断；有可执行测试环境 | 成本与延迟波动大、"昂贵的失败"[50]；补丁冗长/过拟合已有测试 [6][48]；工具链原始（多数只有 bash，缺调试器与程序分析器）[6][7] |
| **B. 无 agent 的 LLM 流水线**（定位—生成—校验固定三段） | Agentless [4]、SRepair（函数级）[14]、Xia 等的直接 LLM 修复研究 [13] | issue 或缺陷函数 + 测试 | SWE-bench Lite 32.00%（96 个正确补丁），单 issue 约 0.70 美元，优于当时所有开源 agent [4]；Defects4J 227 个单函数缺陷，超此前 APR ≥26%，且不需要语句级定位 [14] | 显著低于 agent，且可预算 [4] | 缺陷范围可先验收敛（单函数/单 hunk）、追求性价比与可复现性 | 无法自主补取上下文；对定位质量敏感；复杂多点修改吃力 |
| **C. 传统测试套件驱动 APR**（模板/搜索/语义合成） | TBar [9]、11 款 Java 工具大规模复评 [10]、效率评估 [11]、综述 [8] | 已知失败测试 + 缺陷定位结果 | TBar：完美定位下 74 个正确/101 个 plausible，标准流水线下 43 个正确（Defects4J）[9]；11 款工具在 5 个基准 2,141 个缺陷上只对 21% 生成补丁，Defects4J 47% 而其他基准仅 10%–30% [10] | 单机可跑、无 token 成本，但候选补丁爆炸：模板类最有效却最低效 [11] | 缺陷类型落在已知修复模式内；有强测试套件；离线批处理 | 泛化性差（换基准就掉）[10]；补丁过拟合测试；只能覆盖模式库内的缺陷 |
| **D. 学习型 APR**（NMT/预训练模型） | CURE [12] | 缺陷行/函数 + 定位 | Defects4J 57 个、QuixBugs 26 个正确修复 [12] | 训练成本高，推理便宜 | 有大规模缺陷修复语料的语言与项目 | 受训练分布限制；被通用 LLM 直接生成超越 [13] |
| **E. 静态分析驱动修复**（告警→补丁） | SapFix [15]、Getafix [16]、InferFix [17]、Sorald [18]、NullRepair [19] | 静态分析器的告警（位置+类别），**不需要失败测试** | Getafix：6 类告警 1,268 个修复，top-1 命中人写补丁 12%–91%（按类别），top-5 覆盖 526/1,268 [16]；InferFix（配 Infer）：top-1 C# 65.6%、Java 76.8% [17]；Sorald：161 个 GitHub 仓库、10 条 SonarQube 规则，修复满足前提的违规 65%（852/1,307）[18]；NullRepair：12 个真实 Java 项目、1,119 个残留空安全错误修复 63% [19] | 与静态分析同量级，可进 CI [16][17] | 缺陷类别明确且可判定（空指针、资源泄漏、规则违规）；无复现测试也能修；需要低误报与语义保持 | 只覆盖分析器能查的类别；不处理需求级/逻辑缺陷；误报会传导为噪声补丁 |
| **F. 自动测试生成/缺陷复现** | TestPilot [20]、CodaMosa [21]、Test Wars 对比 [22]、TestGen-LLM [23]、ACH [24]、LIBRO [25]、SWT-Bench [26]、Otter [27] | 待测函数/类，或缺陷报告、issue | TestPilot：25 个 npm 包 1,684 个 API 函数，中位语句覆盖 70.2%、分支 52.8%（Nessie 为 51.3%/25.6%）[20]；Test Wars（GitBug-Java）：LLM 覆盖率落后 EvoSuite 与符号执行，但变异得分显著更高、故障检出更弱 [22]；LIBRO：Defects4J 33%（251/750）生成复现测试，149 个排第一 [25] | LLM 方案按 token 计费；SBST 只耗 CPU | 需要回归护栏、覆盖率补齐、把缺陷报告变成可执行复现 | 覆盖率不等于查错能力 [22]；oracle 质量是瓶颈；生成测试可能只是"观察式打印"而非断言 |

## 二、同一子任务的头对头对比（可比性更强的三组）

### 1) 缺陷定位：agent 式 vs 传统频谱/学习式

| 方案 | 评测集 | 结果 | 备注 |
|---|---|---|---|
| AutoFL（LLM + 函数调用浏览仓库）[28] | 798 个 Java/Python 真实缺陷 | 方法级 acc@1 相对基线最高提升 233.3%，并给出自然语言解释（开发者访谈偏好少而精的解释） | 解释性是相对传统频谱定位的额外收益 |
| AgentFL（多 agent，理解—导航—确认）[29] | Defects4J v1.2（395 个缺陷） | Top-1 命中 157 个，平均 0.074 美元、97 秒/缺陷，与学习式技术互补 | 首次把 LLM 定位从"方法/类"尺度推到项目尺度 |
| ChatGPT-3.5/4 直接定位 [30] | Defects4J | **函数级**上 GPT-4 优于所有既有定位技术，Top-1 比 SmartFL 高 46.9%；**类级**上下文一放大，反而比 SmartFL 低 49.9% | 说明"上下文越多越好"不成立，是 agentic 检索存在价值的直接理由 |

**读法**：LLM/agent 在"有解释、能跨文件"上确有增量，但一旦上下文超出其有效窗口就迅速退化 [30]；传统频谱定位仍是 agent 内部常用的信号源（AutoCodeRover 在有测试套件时就直接调用频谱定位来收窄上下文 [2]）。

### 2) 缺陷复现测试：LLM 少样本 vs agent 式（同一批工业缺陷）

Google 在自家 issue tracker 的 80 个人报缺陷上做了直接对照：LIBRO（少样本 prompt 式）plausible 复现率 10%，**BRT Agent（微调模型 + agent 式编辑）达到 28%**；把生成的复现测试喂给 Google 内部 APR 系统后，**得到 plausible 修复的缺陷数增加 30%**；用复现测试做候选补丁排序（Ensemble Pass Rate），20 个候选中 top-1 命中 plausible 修复的比例为 70% [32]。这是目前"agentic 相对非 agentic 优势"最干净的一组工业对照。

在开源侧，SWT-Bench 给出另一个方向的证据：**为修复而设计的代码 agent 生成的测试，反而优于专门的测试生成系统**；并且生成测试作为补丁过滤器可以让 SWE-Agent 的补丁精度翻倍 [26]。Otter 则把这一任务基准化（TDD-Bench Verified，449 个真实 issue），用规则分析校验并修复 LLM 输出后，fail-to-pass 率优于此前最强系统 [27]。

反向证据同样存在：对 SWE-bench Verified 上六个强模型轨迹的分析发现，**agent 自发写测试的频率在"已解决"和"未解决"任务上没有差别**，这些测试大多充当打印式的观察反馈而非断言校验，用 prompt 干预写测试的多少也不改变最终解决率 [52]；对六个修复系统在 SWE-bench Verified 上的对照也显示，各系统在文件级/符号级定位准确率与缺陷复现能力上差异明显，短板同时来自模型本身与 agentic 流程设计 [5]。换言之"agent 会写测试"本身不构成优势，**把测试当作显式校验环节**（Agentless 的第三段 [4]、BRT+EPR [32]、SWT 过滤 [26]）才构成优势。

### 3) 修复本身：agent vs 流水线 vs 静态分析专用

- **agent vs 流水线**：Agentless 用固定三段流水线在 SWE-bench Lite 上拿到 32.00%、单 issue 0.70 美元，当时高于所有开源 agent [4]；这是"复杂自主性未必换来正确率"的关键反例。但在 OSS-Fuzz 的安全补丁场景，结论相反：作者定制 AutoCodeRover 后发现**agent 的自主性是成功打补丁的关键，Agentless 这类固定控制流不适用**，并指出补丁质量不能用 CodeBLEU 之类的相似度衡量，必须跑漏洞触发输入 [35]。**结论：控制流该固定还是该自主，取决于诊断信息是否需要动态探索**。
- **agent vs 静态分析专用修复**：NullRepair 在 12 个真实 Java 项目上，用静态分析划分符号的安全/不安全使用区域、按人工归纳的决策流程驱动 LLM，修好 63% 的残留空安全错误；对照的两个基线正是"单轮 prompt"和 **mini-SWE-agent**，NullRepair 在语义保持上明显更好（10/12 个项目应用全部补丁后单测全绿，其余两个≥98%）[19]。这说明**在类别明确的告警上，"静态分析结构 + LLM"优于"通用 agent 自由探索"**。
- **混合最优的证据**：在大规模内部代码库上，把静态分析与测试执行轨迹作为符号反馈接入 ReAct agent 的消融实验显示，符号信息对神经 agent 有正向增益，最终离线解决率 42.3%（平均 11.8 轮反馈）[34]；测试生成侧 CodaMosa 也证明"SBST 卡住时用 LLM 提供样例测试再继续搜索"在 486 个基准上显著优于纯 SBST 与纯 LLM [21]。

## 三、agentic 到底强在哪（有证据的四条）

1. **任务边界更宽**。传统 APR 的输入是"失败测试 + 定位结果"，SWE-bench 把输入换成自然语言 issue + 整个仓库，最强模型初期只能解 1.96% [42]；agent 的价值首先体现在把这个任务变得可做（12.5%→19%→30%+ 区间）[1][2][4]。
2. **交互接口本身有效**。SWE-agent 的核心贡献是 agent-computer interface（专为模型设计的读写、导航、执行接口），这被证明是相对非交互式模型的主要增益来源 [1]；debug-gym 进一步把 pdb 这类交互调试器纳入 agent 可用工具集 [7]。
3. **端到端串联**：定位→复现→修补→验证在一个循环里闭合，能用执行反馈自我纠错；工业数据显示每个补丁平均需要 11.8 轮反馈迭代 [34]，这种迭代深度是一次性生成式方法拿不到的。
4. **速度**：AutoCodeRover 平均 4 分钟解决一个 issue，同批 issue 人类平均耗时 2.68 天 [2]；AgentFL 单缺陷定位 0.074 美元/97 秒 [29]。

## 四、agentic 不占优甚至落后的场景（同样有证据）

1. **类别明确的静态告警**：Getafix/InferFix/Sorald/NullRepair 的命中率（12%–91% top-1 按类别、65.6%/76.8% top-1、65% 违规修复率、63% 残留错误修复率）都建立在"不需要失败测试、可进 CI、语义保持可验证"之上，且 NullRepair 直接跑赢 mini-SWE-agent [16][17][18][19]。
2. **覆盖率导向的测试生成**：在 GitBug-Java 上，LLM 方案覆盖率落后 EvoSuite（SBST）与 Kex（符号执行），故障检出能力也更弱，只在变异得分上领先，且对被测类规模高度敏感 [22]。
3. **成本/预算敏感的批处理**：Agentless 以更低成本取得更高分 [4]；SWE-Effi 指出 agent 存在"token 雪球"和"昂贵的失败"（在无解任务上烧掉大量资源），并存在 token 预算与时间预算下有效性排序不一致的现象 [50]。
4. **需要可审计与责任归属时**：agent 补丁冗长、易过拟合已有测试，多数 agent 缺少调试器与程序分析器 [6]；合并后的质量分析显示"合并成功"并不等于"质量合格"，agent 修复 PR 引入的问题以 code smell 为主，按代码改动量归一后不同 agent 差异基本消失 [38]。

## 五、真实项目评测证据（按证据强度分层）

### A. 工业生产环境（最强，但多为内部数据、不可复现）

| 来源 | 规模与设计 | 关键结果 |
|---|---|---|
| Google，agent 式修复评测 [31] | 178 个来自内部 issue tracker 的缺陷（78 个人报 + 100 个机器报告），Passerine（类 SWE-agent）+ Gemini 1.5 Pro，采样 20 条轨迹 | 通过缺陷测试（plausible）：机器报告 73%、人报 25.6%；人工核对语义等价于开发者补丁：机器报告 43%、人报 **17.9%**；并指出企业缺陷在语言多样性、规模、改动分散度上与 SWE-bench 分布不同 |
| Google，agent 式缺陷复现 [32] | 80 个人报工业缺陷，与 LIBRO 直接对照 | BRT Agent 28% vs LIBRO 10%；接入 APR 后 plausible 修复缺陷数 +30% |

| Microsoft InferFix [17] | 与 Infer 配对，在 CI 流水线中做检测—分类—定位—修复—校验闭环 | top-1 C# 65.6%、Java 76.8% |

### B. 真实开源项目（可复现性中等偏上）

- **OSS-Fuzz 安全补丁** [35]：基于真实模糊测试发现的漏洞数据，定制 AutoCodeRover 用漏洞触发输入抽取修复相关代码元素；结论是 agent 自主性有用、相似度指标不可靠。
- **CVE-Bench** [36]：509 个 CVE、4 种语言、120 个热门开源仓库，提供黑盒/白盒测试环境并允许调用静态分析工具；**SWE-agent 最好只修复 21%**，且不会有效使用分析工具。
- **GitHub 上的 agent PR** [37]：157 个开源项目、567 个由 Claude Code 生成的 PR，**83.8% 最终被合并**，其中 54.9% 未经修改即合入，45.1% 需要人工再改（缺陷修复、文档、项目规范符合度尤甚）。
- **合并之后的质量** [38]：AIDev 数据集中 1,210 个已合并的 agent 缺陷修复 PR，用 SonarQube 对 base 与 merge 提交做差分；结论是合并成功不能反映合并后质量，需要系统化质量门。
- **补丁安全性** [51]：覆盖 20,000+ GitHub issue 的大规模安全分析，比较开发者补丁、独立 LLM（Llama 3.3 70B）与三个 agent 框架（OpenHands、AutoCodeRover、HoneyComb），发现独立 LLM 引入大量新漏洞且模式与开发者不同。

### C. 公开基准（可复现性最好，但效度问题最严重）

底座与扩展：SWE-bench（2,294 个真实 issue，12 个 Python 仓库）[42]、Multi-SWE-bench（7 种语言、1,632 个实例，用 Agentless/SWE-agent/OpenHands 三种范式统一评测）[43]、SWE-bench-Live（2024 年后的 1,319 个任务、93 个仓库，每任务独立 Docker，专治过时与污染）[44]；缺陷修复侧仍以 Defects4J [45] 与更新的 GitBug-Java（55 个仓库 2023 年提交、199 个缺陷）[46] 为主。

**已被量化的效度问题（读公开分数时必须打折）**：

- **解法泄漏与弱测试**：SWE-bench 中 32.67% 的成功补丁属于解法直接写在 issue 或评论里，31.08% 属于测试太弱而"蒙混过关"；过滤后 SWE-Agent+GPT-4 的解决率从 12.47% 掉到 **3.97%**；超过 94% 的 issue 创建于模型知识截止之前 [47]。
- **通过测试 ≠ 正确**：对三个 SOTA issue 求解工具在 SWE-bench Verified 上的补丁做差分测试，7.8% 的补丁通过 SWE-bench 校验却通不过开发者测试套件，29.6% 的 plausible 补丁与真值补丁行为不同（其中 28.6% 经人工确认确实错误），合计使报告的解决率虚高 **6.2 个百分点** [48]。
- **记忆化**：只给 issue 描述、不给仓库结构，SOTA 模型就能以最高 76% 的准确率说出缺陷文件路径；换到非 SWE-bench 仓库只有 53%，函数复现的 5-gram 重合度也从 35% 降到 18% [49]。
- **成本维度缺失**：主流榜单只看解决率，SWE-Effi 在同一子集上引入 token/时间预算后排名重排，并暴露"昂贵的失败"[50]。

### D. 人因与随机对照（最贴近"到底有没有用"）

- **受控用户研究**（40 名开发者、中位 6 年经验、9 个真实 Java 开源缺陷、160 次调试会话，工具为 Recoder/SimFix/TBar）：拿到**正确**的 APR 建议使调试成功几率相对只有测试时提升约 14,000%，而"欺骗性建议"（通过全部现有测试但不满足真实规约）使成功几率**下降 65%**；开发者总体对 APR 印象正面 [40]。这条结论对 agentic 同样适用：**补丁质量的方差比平均值更要命**，也解释了工业界为何要专门做弃权与校验策略 [33]。
- **随机对照试验**（经验丰富的开源开发者，在自己平均维护 5 年的成熟仓库上完成 246 个任务，随机分配是否允许使用 2025 年前沿 AI 工具）：**允许使用 AI 反而使完成时间增加 19%**，而开发者事前预计缩短 24%、事后自评缩短 20% [41]。这是目前对"AI 辅助=提效"最有力的反证，提醒不要把基准解决率外推成生产力收益。

## 六、证据强度总结与阅读建议

| 结论 | 证据强度 | 依据 |
|---|---|---|
| agent 能在"issue→整仓补丁"这一任务上产出可用补丁 | **强**（多来源、含工业部署与开源 PR 合并数据） | [1][2][4][31][34][37] |
| agent 在企业真实缺陷上的语义正确率远低于公开榜单 | **强**（工业内部人工核对） | 人报缺陷 17.9% 语义等价 [31]；生产落地 25.5% [34]；CVE 修复 21% [36] |
| 类别明确的静态告警修复上，静态分析驱动方案更优 | **中–强**（多工具、真实仓库、含与 agent 的直接对照） | [16][17][18][19] |
| 覆盖率导向测试生成上传统方法仍占优 | **中**（单篇多工具对比，评测集为 GitBug-Java） | [22]，另见 [20][21] |
| agent 式复现测试优于少样本 LLM 复现 | **中–强**（工业同批缺陷直接对照 + 开源基准） | [32][25][26][27] |
| 公开榜单分数存在系统性虚高 | **强**（三条独立路径：泄漏、弱测试、记忆化） | [47][48][49] |
| "用了 agent 就更快"在真实开发中未被证实 | **中**（单项 RCT，样本有限但设计严格） | [41]，与受控用户研究 [40] 互补 |

**读数字的三条纪律**：
1. **先看定位假设**。TBar 在"完美定位"下 74 个正确、在真实流水线下只剩 43 个 [9]；SRepair 的卖点之一正是不需要语句级定位 [14]。凡是不说明定位来源的分数都不可比。
2. **区分 plausible 与 correct**。工业与学术都反复出现这一裂口：Google 数据里 plausible 73% 对应语义正确 43%（机器报告）、25.6% 对应 17.9%（人报）[31]；SWE-bench 上 29.6% 的 plausible 补丁行为与真值不同 [48]。
3. **把成本与噪声计入指标**。agent 的每缺陷成本从 0.14 美元 [3]、0.70 美元 [4] 到"昂贵的失败"不等 [50]；而工业上真正决定能否上线的是评审噪声——弃权+校验能把成功率抬高最多 39 个百分点 [33]，Bloomberg 的做法是把补丁塞进正确的 PR 与正确的人面前，接受率做到 74.56% [39]。

## 七、场景选型清单

| 场景 | 首选 | 理由与证据 |
|---|---|---|
| 静态分析告警治理（空指针、资源、规则违规） | 静态分析驱动修复（模板/学习式/结构化 LLM 工作流） | 无需失败测试、可进 CI、语义保持可验证；[16][17][18][19] |
| CI 里的测试失败自动修复 | agentic + 符号反馈（静态分析 + 测试轨迹）+ LLM-as-a-Judge + 人评审 | 生产验证的完整闭环与落地率数据；[34]，降噪见 [33] |
| 用户报的功能性 issue（跨文件、描述模糊） | agentic（必要时先跑 agent 式复现测试） | 复现测试使 plausible 修复 +30%，并可用于补丁排序；[32][2][27] |
| 成本敏感的批量修复 / 需要可复现流水线 | 无 agent 的三段式流水线 | 更高分且成本可预算；[4][14] |
| 安全漏洞修复（有触发输入/PoC） | agentic（动态证据驱动），慎用固定控制流 | OSS-Fuzz 经验与 CVE-Bench 上限；[35][36] |
| 回归护栏与覆盖率补齐 | SBST/符号执行为主，LLM 补盲区 | 覆盖率与故障检出仍占优，LLM 变异得分更高、可混合；[22][21][20] |
| 隐私/合规等特定回归的加固 | 变异引导 + LLM 测试生成 | 工业规模验证与 73% 接受率；[24][23] |
| 任何方案上线前 | 强制"弃权 + 补丁校验 + 差分测试 + 合并后质量门" | [33][48][38][40] |
