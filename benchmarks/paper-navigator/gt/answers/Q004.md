# 多智能体写代码为什么"有时候"比单 agent 稳：任务拆分、工具调用、测试反馈三套机制

## 0. 结论先说

多智能体之所以"有时候"更稳，不是因为"人多力量大"，而是因为它把**生成**和**验证**这两件事从同一个上下文里拆开了。单个 agent 做自我修复时，瓶颈不在"改代码的能力"，而在"发现自己错在哪的能力"——这一点在 *Is Self-Repair a Silver Bullet for Code Generation?* 里有直接实验证据：把反馈来源换成更强的模型或人类之后，收益立刻大幅上升，而模型自己给自己反馈时收益很小甚至为零 [3]；*Large Language Models Cannot Self-Correct Reasoning Yet* 进一步指出，纯内生（无外部反馈）的自我纠正常常反而掉点 [4]。

于是"更稳"的三条落地路径正好对应你问的三套机制：

| 机制 | 它到底解决什么 | 稳定性来源 |
| --- | --- | --- |
| 任务拆分 | 上下文预算超限、长轨迹里的误差累积 | 每个 agent 的输入更短、目标更单一；中间产物结构化，错误在阶段边界被截断 |
| 工具调用 | 模型"凭想象"判断代码对不对 | 把判断权交给解释器 / 编译器 / 文件系统等**外部确定性反馈源** |
| 测试反馈 | 缺少可自动求值的正确性信号 | 用可执行的测试把"对不对"变成布尔量，形成可迭代的闭环 |

而"有时候"这个限定词同样有论文依据：验证器不完美时收益有硬上界 [29]，调用数增加时性能非单调 [30]，多智能体系统的主要失败恰恰集中在"任务验证"这一类 [32]，而一条精心设计的固定流水线可以打赢复杂的自主 agent [33]。

---

## 1. 机制总览：稳定性来自"生成-验证解耦"

先把因果链摆清楚，后面三节再逐条展开。

**(a) 单体迭代的天花板。** *Self-Refine* 用同一个 LLM 同时充当 generator / feedback provider / refiner，在 7 类任务上平均带来约 20 个百分点的绝对提升 [1]；*Reflexion* 则把环境反馈语言化后写入 episodic memory，指导下一轮试验，在 HumanEval 上把 pass@1 推到 91% [2]。这两条路线证明"迭代"本身有用。

**(b) 但迭代的增益依赖反馈质量，而不是修复能力。** *Is Self-Repair a Silver Bullet* 在 HumanEval 与 APPS 上分析 Code Llama / GPT-3.5 / GPT-4，发现**把修复的采样成本折算进去之后**，自修复的收益往往很小、在数据子集间波动很大、有时干脆不存在；作者的假设是"自修复被模型给自己代码写反馈的能力卡住了"，并用更强模型伪造高质量反馈、以及让人类给 GPT-4 提供反馈这两个对照实验验证了这个假设 [3]。*LLMs Cannot Self-Correct Reasoning Yet* 从推理任务侧给出同向证据：没有外部反馈时，自我纠正会让性能下降 [4]。

**(c) 所以关键是引入"异质的、非自证的"反馈源。** *CRITIC* 把这件事说得最直白：LLM 是黑盒，要靠外部工具（搜索引擎、代码解释器）交叉检查后再修订，论文明确强调"外部反馈对持续自我改进至关重要" [5]。*Improving Factuality and Reasoning in Language Models through Multiagent Debate* 则给出另一种异质来源——多个模型实例互相提出并辩驳各自的推理过程，多轮后收敛到共同答案，可以降低幻觉与谬误 [6]。

一句话：**多智能体是"制造外部反馈"的一种工程手段**。任务拆分负责让反馈可定位，工具调用负责让反馈可信，测试反馈负责让反馈可自动求值。

## 2. 机制一：任务拆分（Task Decomposition）

### 2.1 数据流骨架

最常见的形态是"角色链"：

```
需求 → [分析/规划 agent] → 结构化中间产物(需求文档/计划/接口)
     → [编码 agent]      → 代码
     → [测试/评审 agent] → 结构化缺陷报告
     → 回流到编码 agent（带定位信息的反馈）
```

关键不在"有几个角色"，而在**箭头上流的是什么**。

### 2.2 角色分工：把一个复杂任务变成若干个简单任务

- *Self-Collaboration Code Generation via ChatGPT* 是最早把这一点讲清楚的代表作：通过 role instruction 让多个 LLM 实例扮演不同"专家"，各自负责复杂任务中的一个子任务，并规定它们如何协作互动，从而组成一个无需人类介入的虚拟团队；论文把软件工程方法论直接搬进框架，落成 analyst / coder / tester 三角色对应分析、编码、测试三个阶段 [7]。
- *MetaGPT* 把这套东西从"角色"升级为"流程 + 界面"。它做了两件对稳定性最关键的事：一是把标准作业流程（SOP）编码进提示词以强化结构化协同；二是**强制模块化输出**（mandate modular outputs），让下游 agent 能校验上游产物，从而抑制多 agent 朴素串联时的**级联幻觉**（cascading hallucination）——论文开篇就把"级联幻觉"点名为复杂任务失败的主因 [8]。这就是"结构化中间产物"这一机制的原始出处。
- *ChatDev* 用瀑布模型把开发切成 design / coding / testing / documenting，靠 **chat chain** 规定"沟通什么"，靠 **communicative dehallucination** 规定"怎么沟通"（助手先主动反问澄清，而不是直接给出可能幻觉的答案）；论文还观察到一个有意思的分工现象：系统设计阶段用自然语言沟通更有利，调试阶段用编程语言沟通更有利 [9]。

### 2.3 阶段流水线：把"人类程序员的完整循环"复刻出来

- *MapCoder* 用四个 agent 复刻人类解题的全周期——**回忆相似例子 → 规划 → 生成代码 → 调试**；规划 agent 会生成多个候选计划并给出置信度，框架按置信度动态遍历这些计划。八个基准上取得当时 SOTA：HumanEval 93.9%、MBPP 83.1%、APPS 22.0%、CodeContests 28.5%、xCodeEval 45.3% [10]。
- 到了仓库级问题（SWE-bench 这类真实 GitHub issue [38]），拆分的形态变成**任务图**与**模块化子代理**：*CodeR* 用多 agent + 预定义 task graph 来编排修复流程，在 SWE-bench lite 上每题只提交一次即可解决 28.33% [11]；*MASAI* 则把问题拆成目标与策略各自明确的子代理，论文列出的三条收益正是拆分机制的教科书式表述——(1) 不同子代理可以用不同的问题求解策略并分别调优，(2) 子代理能从仓库中分散的不同来源采集信息，(3) **避免不必要的长轨迹**，后者会抬高成本并混入无关上下文；同样在 SWE-bench Lite 上达到 28.33% [12]。

### 2.4 上下文分摊：拆分最"物理"的那层收益

*Self-Organized Agents (SoA)* 把这层收益单独拎出来做成机制：每个 agent 只负责自己那一小块代码，**随问题复杂度自动"繁殖"出新 agent**；于是整体代码量可以随 agent 数量无限增长，而每个 agent 管理的代码量保持恒定 [13]。这解释了为什么在长代码 / 大仓库场景下多 agent 常常不是"更聪明"，只是**没有被上下文长度打垮**。

### 2.5 规模与拓扑：拆到多细才划算

*Scaling Large-Language-Model-based Multi-Agent Collaboration (MacNet)* 用有向无环图把 agent 组织成协作网络，让推理与指令沿拓扑传播。两个发现对工程直接有用：一是支持上千 agent 协作，且**不规则拓扑优于规则拓扑**；二是存在一条**协作 scaling law**——整体性能随 agent 数量呈 logistic 增长，而且"协作涌现"出现得比传统神经网络涌现更早 [14]。

### 2.6 拆分的反面：planner-coder gap

拆分不是免费的，它引入了新的失效面。*Understanding and Bridging the Planner-Coder Gap* 用变异测试（语义保持的变异算子 + 专门的 fitness function）系统评估主流多 agent 系统，发现语义等价的输入会造成剧烈性能塌陷：原本能解的问题里有 **7.9%–83.3%** 会失败；失败归因显示 **75.3%** 来自 planner 与 coder 之间的信息丢失，即"planner-coder gap" [15]。**这条证据同时解释了"为什么 MetaGPT 强调结构化输出"**：阶段之间传递的如果是松散的自然语言，拆分带来的收益会被信息丢失吃掉。

## 3. 机制二：工具调用与执行环境

### 3.1 基本闭环：ReAct

*ReAct* 把推理轨迹与任务动作交错生成：推理帮助模型归纳、跟踪、更新行动计划并处理异常，动作则让模型接入外部知识库或环境去获取信息；论文明确指出这套交错方式能**缓解链式思考里普遍存在的幻觉与误差传播** [16]。所有代码 agent 的 `thought → action → observation` 循环都是它的后代。

### 3.2 动作空间设计：CodeAct

*Executable Code Actions Elicit Better LLM Agents* 指出，用 JSON / 固定文本格式表达动作有两大硬伤：动作空间受限于预定义工具，以及无法组合多个工具。CodeAct 改用**可执行 Python 代码作为统一动作空间**，配一个 Python 解释器，于是 agent 能复用已有软件包、能用控制流组合工具、并且能**在多轮交互中根据新的 observation 动态修订先前动作**。在 API-Bank 和自建的 M3ToolEval 上对 17 个 LLM 做分析，成功率最高提升约 20% [17]。这一条对"稳"的贡献是：**动作本身可执行 ⇒ 每一步都自带正确性信号**。

### 3.3 接口设计：SWE-agent 的 ACI

*SWE-agent* 提出的核心论点是"LM agent 是一类新的终端用户，需要为它专门设计接口"。它的 agent-computer interface（ACI）包含定制的文件查看器、带 linter 的编辑命令（编辑后若语法不合法就拒绝提交并返回错误）、仓库级搜索命令与紧凑的环境反馈格式；这些接口显著提升了 agent 创建/编辑文件、浏览整个仓库、执行测试与程序的能力，在 SWE-bench 与 HumanEvalFix 上分别取得 12.5% 与 87.7% 的 pass@1，远超此前的非交互式方案 [18]。**这是"稳定性来自护栏而不是来自模型"最干净的证据**：同样的模型，换一套接口，成绩差一大截。

### 3.4 工具作为"可信裁判"：CRITIC

*CRITIC* 的流程是"初始输出 → 与合适的工具交互以评估某些方面 → 基于验证反馈修订"，在自由问答、数学程序合成、毒性削减三类任务上都稳定提升，并把结论上升为一般性原则：**外部反馈对持续自我改进至关重要** [5]。放到写代码的语境里，"工具"就是解释器、类型检查器、静态分析器和测试运行器。

### 3.5 通用底座：AutoGen

*AutoGen* 把上述要素抽象成"可对话 agent + 可编程会话"的通用框架，agent 可以由 LLM、人类输入、工具或它们的组合来驱动，开发者用自然语言和代码共同定义交互模式 [19]。工程上大多数多 agent 代码系统的"工具执行 + 人在环"这一层，都落在这类底座上。

## 4. 机制三：测试反馈闭环

这是三套机制里唯一能提供**自动可求值的正确性信号**的一套，也因此是"稳"的主要来源。

### 4.1 反馈信号从哪来：自生成测试与双向执行一致性

*CodeT* 的做法是让同一个预训练模型既生成 n 份代码样本、又生成 m 个测试用例，然后交叉执行，做 **dual execution agreement**：既看代码输出与生成测试是否一致，也看不同代码样本之间输出是否互相一致 [20]。实现上，通过同一组测试的代码被聚成一个"共识集"，用集合内的代码数与测试数共同给该共识集打分并排序——这就是"测试和代码互为验证"这一思路的数学形式，也是后来所有"自生成测试"路线的祖先。

### 4.2 反馈粒度：从"跑挂了"到"第几个基本块挂了"

- *Teaching Large Language Models to Self-Debug* 提出 Self-Debugging：用少样本示范教模型做"小黄鸭调试"——**在没有任何人类反馈、也没有错误信息的情况下**，模型通过考察执行结果并用自然语言逐行解释自己的代码来定位错误。在 Spider（没有单元测试可验证）上，加入代码解释后稳定提升 2–3 个百分点，最难那一档提升 9 个百分点；在 TransCoder 与 MBPP 这类有单元测试的场景收益更大 [21]。
- *Debug like a Human (LDB)* 把粒度再切细：既有工作把生成的程序当成一个不可分割的整体，而人类开发者会打断点、逐段查看运行时信息。LDB 因此**把程序切成基本块（basic blocks），在运行过程中记录每个基本块执行后中间变量的取值**，让 LLM 逐块验证正确性，再据此修复 [22]。反馈从"这个函数不对"变成"第 3 个基本块之后 `i` 的值就已经不对了"，这是把反馈信噪比拉高最关键的一步。

### 4.3 角色隔离：测试不能由写代码的那个上下文来写

*AgentCoder* 的三角色设计——**programmer agent / test designer agent / test executor agent**——把这条约束显式化：programmer 只管生成与按反馈重构代码，test designer 独立生成测试用例，test executor 在本地环境跑代码 + 测试并把结果写回给 programmer [23]。这正好对应第 1 节的因果链：自修复失效是因为反馈来自同一个"自我"，把出题人和答题人分开，就等于人工制造了一个异质反馈源。

### 4.4 把反馈当"梯度"：文本反向传播与执行奖励

- *EvoMAC* 把多 agent 协作网络类比成神经网络来训练：通过把网络输出与目标 proxy 对照拿到**文本形式的环境反馈**（编译 / 测试输出），再用一种新的 **textual backpropagation** 去更新这张网络（更新 coding team 的 agent 及其连接与提示）。同时它提出面向需求的软件级基准 rSDE-Bench，其自动评估与人工评估高度一致 [24]。这套机制把"测试反馈"从一次性修补升级成**对团队结构本身的优化信号**。
- *RLEF* 走的是训练侧：用端到端强化学习教模型利用执行反馈，在竞赛编程任务上让 8B 与 70B 模型都刷到新 SOTA，并把所需样本量降低一个数量级；推理期行为分析显示模型确实学会了跨多步有效利用自动反馈 [25]。论文的动机陈述本身就是重要证据：**当前 SOTA LLM 在"迭代改代码"上并不比"独立多次采样"更强**——除非专门训练过。

### 4.5 测试到底值多少：正面与反面的量化证据

- 正面：*SWT-Bench* 系统评估代码 agent 把用户 issue 形式化成测试用例的能力，发现为代码修复设计的 agent 在测试生成上反而超过专门的测试生成系统，并给出一条对工程最有用的结论——**生成的测试作为候选补丁的过滤器非常有效，能把 SWE-Agent 的 precision 翻倍** [26]。这是"测试反馈提升稳定性"最直接的量化。
- 反面：*Rethinking the Value of Agent-Generated Tests* 分析六个强模型在 SWE-bench Verified 上的轨迹，发现同一模型里"解决了"与"没解决"的任务写测试的频率相近；而且 agent 写的所谓测试，更多是**观察性反馈通道**——带信息的 print 语句远多于断言式检查 [27]。也就是说，很多号称"测试驱动"的 agent 实际上只是在用测试当打印调试，机制没有真正闭合。

## 5. 把三套机制合起来：为什么是"有时候"

这一节是回答"有时候"三个字的关键，涉及可以量化的统计机制。

**(a) 覆盖率能涨，挑不出来就白涨。** *Large Language Monkeys* 显示，coverage（任意一个采样解正确的题目比例）随采样数在四个数量级上呈近 log-linear 增长，可用指数幂律建模；**在有自动验证器的领域（代码、形式化证明），coverage 的提升能直接转化为性能提升**——在 SWE-bench Lite 上，DeepSeek-Coder-V2-Instruct 从 1 个样本的 15.9% 涨到 250 个样本的 56% [28]。多智能体的"多次生成 + 多次评审"本质上是在花这份采样预算，所以**验证器好不好用，决定了这份预算能不能兑现**。

**(b) 验证器不完美会给收益封顶。** *The Limits of Inference Scaling Through Resampling* 证明：当验证器有非零假阳性率时，重采样**无法降低**这个假阳性概率，因此不论算力多大，基于重采样的推理扩展都存在准确率上界。论文在 HumanEval / MBPP 上观察到模型单样本准确率与其假阳性率强相关（这两个基准的单元测试覆盖有限），并给出一条很反直觉的实用结论——**最优采样次数常常少于 10 次**，因为假阳性的负效用会盖过继续采样的收益 [29]。这正是"多 agent 反复自测反而越修越歪"的理论解释。

**(c) 更多调用不等于更好。** *Are More LLM Calls All You Need?* 研究 Vote / Filter-Vote 这类复合推理系统，发现性能随 LLM 调用数**非单调**：调用数增加对简单查询有利、对困难查询有害，两者叠加出先升后降的曲线 [30]。多 agent 系统本质上就是一种复合推理系统。

**(d) 增益主要来自"多样性 + 选择"，而不是"对话"。** *Diversity Empowers Intelligence (DEI)* 把这一点做成了可复现的工程结论：在已有 SWE agent 之上挂一个 meta-module 来管理"agent 委员会"并从候选补丁中挑选，一组个体最好成绩只有 27.3%（SWE-Bench Lite）的开源 agent 组合后达到 34.3%（相对提升 25%），最佳组合达到 55% [31]。换句话说，**多智能体真正稳定的那部分收益，来自"多路生成 + 有效选择"这个集成机制**，与第 1 节的辩论证据 [6] 同源，但更可控。

## 6. 什么时候多智能体反而不稳（边界条件）

1. **验证与终止环节才是主要失效面。** *Why Do Multi-Agent LLM Systems Fail?* 收集 7 个主流 MAS 框架上 1600+ 条标注轨迹，通过对 150 条轨迹的严格分析建立首个多智能体失败分类法 MAST：**14 种失败模式，归为三大类——系统设计问题、智能体间对齐失败（inter-agent misalignment）、任务验证（task verification）** [32]。这条证据直接说明：你上面搭的拆分和工具调用再漂亮，验证这一环不闭合，多 agent 的收益就是浮的。
2. **固定流水线可能打赢自主 agent。** *Agentless* 用最朴素的三阶段——**定位 → 修复 → 补丁验证**，完全不让 LLM 自己决定下一步动作、也不用复杂工具，在 SWE-bench Lite 上取得 32.00%（96 个正确修复）且成本仅 $0.70，超过当时所有开源 agent 方案 [33]。要点在于：**它保留了工具调用与测试验证，砍掉的是"自主规划"**——恰好印证前三节的机制排序。
3. **多轮沟通会引入从众效应。** *Talk Isn't Always Cheap* 发现，即使强模型在数量上占优，辩论也可能让准确率随轮次下降；模型频繁在同伴推理面前**从正确答案倒向错误答案**，倾向于附和而不是质疑有缺陷的推理；作者进一步分析了谄媚（sycophancy）、社会从众等成因 [34]。
4. **有没有执行反馈，比拓扑长什么样重要得多。** *Feedback Over Form* 在 1–3B 小模型上用 NEAT 式演化搜索比较各种流水线结构，结论是：**带执行反馈的自我精炼在 HumanEval 与 MBPP 上带来超过 4 个标准差的提升，而更复杂的拓扑结构并没有在简单精炼循环之外带来额外收益**；机制上，精炼主要修好运行时错误（NameError、SyntaxError），**很少能修 AssertionError 这类逻辑错误**；并且提前停止是必需的，否则每一轮迭代的净收益都是负的 [35]。这三条几乎可以直接当作工程 checklist。
5. **多 agent 可以被"单 agent + 技能库"替代。** *When Single-Agent with Skills Replace Multi-Agent Systems and When They Fail* 把技能视作内化的 agent 行为，从而把一个多 agent 系统"编译"成等价的单 agent 系统，用技能选择换掉 agent 间通信；实验显示能显著降低 token 与延迟而保持相当的准确率——但同时揭示了新的失效点：**技能选择存在类似人类决策的有界容量，技能库变大后选择准确率会退化** [36]。
6. **别忘了代价。** *Enhancing LLM Code Generation* 在 19 个 LLM 上系统评测"多 agent 协作"与"基于运行时执行信息的调试"各自以及组合后的效果，评估维度里显式包含**延迟**（latency）与可靠性，而不只是准确率 [37]。工程上这条最容易被忽略。

## 8. 建议的阅读顺序

1. 先读 [3] 和 [4]，建立"为什么单 agent 自修复不够"的问题意识；
2. 再读 [7][8][9] 看任务拆分的原型，[10][11][12] 看它在竞赛题与仓库级问题上的两种形态；
3. 工具那一支读 [16] → [17] → [18]，能清楚看到"动作空间 → 接口设计"的演进；
4. 测试反馈那一支读 [20] → [21] → [22] → [23] → [24]，粒度从粗到细、从推理期到训练期；
5. 最后读 [29][30][32][33][35]，把"什么时候不该上多智能体"这条线补齐；综述层面可用 [39] 做地图，评测底座用 [38] 与 [26]。
