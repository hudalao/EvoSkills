# 代码智能体的演进脉络：从代码补全、自动程序修复到仓库级任务执行

本文只在软件工程与代码智能体方向内部梳理，按“任务范式—评测方式—代表论文”三条线索，把 2009 年至 2026 年的关键工作串成一条可追溯的技术演进链。

## 零、总览：三条相互缠绕的主线

这条脉络不是单一技术的线性升级，而是三条线同时推进、彼此约束：

- **任务范式**：token 级续写 → 缺陷补丁生成 → 独立函数/类级生成 → 跨文件仓库级编辑 → 端到端“读 issue、改仓库、跑测试、交补丁”的自主执行。
- **评测方式**：困惑度与 token 准确率 → “补丁能否通过测试”并引入过拟合审查 → pass@k 功能正确性 → 仓库级执行式评测 → 环境化、多语言、长程、抗污染的评测。
- **能力载体**：n-gram/RNN 语言模型 → seq2seq 与预训练编码器-解码器 → 通用大模型 → 大模型加工具与环境构成的智能体 → 用强化学习与合成环境专门训练出来的智能体。

## 一、阶段一（2012–2019）：代码“可预测”，补全成为研究对象

这一阶段的起点是一个经验发现：真实软件代码在统计意义上高度重复、可预测，因此可以像自然语言一样被 n-gram 语言模型建模，并直接用于提升 IDE 的补全建议 [1]。随后的工作把这一思路系统化：基于决策树与领域特化的概率模型，把补全从“按频率排序候选”推进到“按程序上下文条件建模下一个 token/API”，并在真实工程代码上取得可用的精度 [2]。到 2018 年，这一子领域已经积累到可以成书式综述的规模，把源代码的概率建模、表示学习与下游应用（补全、命名、缺陷预测等）整理成统一框架 [3]。

范式特征：任务是**局部续写**，输入是光标前后的上下文，评测靠困惑度与 Top-k 命中率，没有“执行”这一环。这也埋下了后续所有争论的种子——统计上像人写的代码，未必是正确的代码。

## 二、阶段二（2009–2019）：自动程序修复确立“生成—验证”范式

与补全线并行、且更早成型的是自动程序修复（APR）。奠基工作把补丁生成形式化为“在已有代码上做变异与重组、再用测试套件做验证”的搜索问题，用遗传编程在真实 C 程序上自动修好了多个缺陷 [4]。此后 APR 分化出三条主要路线：

- **基于搜索/启发式**：延续 [4] 的变异—验证循环。
- **基于语义与约束求解**：把修复位置的期望行为抽象成约束，用符号执行与程序合成直接推导补丁表达式 [5]。
- **基于模板/人写补丁学习**：从大量历史人工补丁中挖掘修复模式，再把模式套用到新缺陷上 [6]。

这一阶段真正的长期影响在**评测方式**。Defects4J 把真实 Java 项目的缺陷、触发测试与修复提交打包成可复现数据集，让“修好了几个 bug”第一次具备横向可比性 [7]。紧接着，一篇关键的反思工作指出：仅靠“通过测试”判定补丁正确会严重高估修复能力，大量补丁只是“看起来对”，即补丁过拟合问题 [8]。“可执行验证 + 验证本身可能不充分”这一对张力，从此贯穿到今天的 SWE-bench 争论。

## 三、阶段三（2017–2021）：修复的神经化

深度学习进入 APR 后，补丁生成被重新表述为序列转换问题。早期代表把学生程序的编译错误修复建模为“错误程序 → 正确程序”的端到端神经翻译 [9]；随后有工作在开源项目的海量 bug-fix 提交上做大规模实证，系统检验神经机器翻译学习真实缺陷修复模式的边界 [10]。这条路线的成熟形态引入了代码感知的搜索与预训练语言模型初始化，把神经翻译式修复推到当时基准上的最好水平 [11]。

范式特征：**任务定义没变（给缺陷、出补丁），但生成器从“搜索+模板”换成了“学习出来的模型”**，评测仍以固定缺陷基准上的正确修复数为准。这一步是后续“大模型直接当修复器”的直接前身。

## 四、阶段四（2020–2023）：预训练与大模型把补全和修复统一起来

预训练代码模型的出现打通了两条线。CodeBERT 用自然语言与编程语言的双模态预训练，为检索、补全、缺陷相关任务提供了统一的通用表示 [12]。真正的分水岭是 Codex 及其配套评测：模型直接从文档字符串生成完整函数，并用 HumanEval 以 pass@k 度量**功能正确性**而非文本相似度 [13]。这一举把代码生成的评测锚点从“像不像”移到了“跑不跑得通”。

与之同步的是评测维度的扩张：一方面，安全研究指出补全模型在安全敏感场景下会稳定产出含漏洞的代码，把“正确性”之外的安全维度纳入评测 [14]；另一方面，EvalPlus 指出既有基准测试用例数量与质量不足，会显著高估模型的功能正确率，主张用自动扩充的测试集重新严格评测 [15]。这实质上是阶段二 [8] 的“补丁过拟合”在大模型时代的重演。

修复线也被同一批模型改写。AlphaRepair 提出零样本、基于代码语言模型填空的修复范式，绕开了对配对训练数据的依赖 [16]；随后有工作系统评估各类预训练大模型直接用于 APR 的效果与规模效应，确认“更大的通用模型 + 少量适配”已能超过精心设计的传统 APR 系统 [17]。再往前一步，修复被改造成**多轮对话与反馈闭环**：把失败测试的输出反馈给模型持续迭代，用极低成本修好了大量缺陷 [18]；同期的自调试工作让模型在没有人类反馈的情况下，通过执行结果与自我解释来定位并纠正自己的代码 [19]。

这一步至关重要：**“生成—执行—读反馈—再生成”的循环被确立下来**，它正是后来智能体的行为骨架。

## 五、阶段五（2022–2024）：上下文从函数扩展到整个仓库

大模型在独立函数上表现优异，但真实工程代码高度依赖跨文件上下文。这一阶段的核心问题是：**如何把仓库塞进（或检索进）有限上下文**。

代表性路线包括：学习为每个补全点生成仓库级提示，从导入关系、父类文件等结构化来源挑选上下文，且不需要访问模型权重 [20]；用相似度检索与生成迭代交替的方式，让检索结果被上一轮生成结果反过来精化 [21]。评测同步跟进，出现了专门度量跨文件仓库级补全的基准 [22]。

更进一步的工作不再把仓库级任务当作“补全”，而当作**变更传播问题**：包迁移、静态检查修复、类型标注这类任务需要在整个仓库里做连锁编辑，于是引入依赖分析与规划，把一次仓库级修改分解成受依赖约束的编辑序列 [23]。评测侧则出现了在代码分布与依赖分布上都与真实仓库对齐、并由开发者人工标注需求与参考依赖的基准 [24]。

至此，“仓库级”已经成为独立任务范式，但执行主体仍是**被调用的模型**，而不是自主行动的智能体。

## 六、阶段六（2023–2025）：SWE-bench 与智能体范式落地

真正的范式跃迁由评测触发。SWE-bench 从 12 个流行 Python 仓库的真实 GitHub issue 与对应 PR 中构造了 2294 个任务实例，要求系统在给定代码库与 issue 描述的条件下自行修改代码库，并用仓库自带测试判定是否解决 [25]。这个定义同时改变了三件事：任务输入变成自然语言 issue 与整个仓库、动作空间变成任意文件编辑、评测变成**端到端执行式**判定。

围绕这个任务，方法侧迅速分化为几条路线：

- **通用智能体 + 专用接口**：SWE-agent 提出智能体—计算机接口（ACI）的概念，认为语言模型是一类新的“终端用户”，需要为其专门设计浏览、编辑、执行的接口，接口设计本身显著影响解决率 [26]。
- **面向程序改进的结构化智能体**：AutoCodeRover 把 issue 解决拆成代码搜索、故障定位与补丁生成，用程序结构信息（AST、类/方法层次）引导检索，把传统 APR 的流水线搬进智能体 [27]。
- **反向的简化路线**：Agentless 质疑复杂自主智能体的必要性，用“定位—修复—验证”的固定三段式流水线，在不做自主规划的前提下取得有竞争力的结果，成为此后长期的强基线 [28]。
- **开放平台与统一动作空间**：OpenHands 提供开源的通用软件开发智能体平台，把编写代码、运行命令、浏览网页统一到一个可扩展环境中 [29]；CodeAct 则从动作表示层面论证，用可执行 Python 代码作为统一动作空间，比预定义 JSON 工具调用更灵活，并能借解释器实现动作的动态修正 [30]。
- **APR 线的合流**：RepairAgent 明确把程序修复交给一个能自主规划、自行调用工具、自由交错“收集信息—收集修复素材—验证补丁”的 LLM 智能体，这是修复线与智能体线正式并轨的标志 [31]。

评测侧同期扩张出两个重要方向：一是**任务类型扩张**，SWT-Bench 把同一批真实 issue 反过来用于考察智能体“把 issue 形式化成测试用例”的能力，测试生成从此成为与修复对称的一等任务 [32]；二是**语言与生态扩张**，Multi-SWE-bench 覆盖 Java、TypeScript、JavaScript、Go、Rust、C、C++，由 68 位标注者从 2456 个候选中人工标注出 1632 个实例，打破 SWE-bench 近乎纯 Python 的局限 [33]。

## 七、阶段七（2025–2026）：智能体本体被训练出来，评测被重新审视

前一阶段的智能体基本是“强模型 + 好脚手架”，2025 年后重心转向**训练智能体本体**，随之而来的是训练环境与数据的工程化：

- SWE-Gym 提供首个可用于训练真实 SWE 智能体的环境，含 2438 个带可执行运行时与单元测试的 Python 任务实例，并用采样轨迹训练验证器做推理期扩展 [34]。
- SWE-smith 针对“数据难造”这一瓶颈，给定任意 Python 代码库自动构造执行环境并合成大量任务实例，把训练数据规模从千级推向更大量级 [35]。
- SWE-RL 首次把基于规则奖励的强化学习扩展到真实软件演化数据上，让模型从海量开源提交中恢复开发者的推理过程与解法 [36]。

与训练同等重要的是**评测的自我修正**。一条线继续追问“解决”的含义：有工作实证检验 SWE-bench 与 SWE-bench Verified 上被判定为“已解决”的补丁，发现相当比例是通过了测试却不符合开发者意图的似是而非补丁 [37]——这正是阶段二补丁过拟合问题 [8] 在智能体时代的第三次重现。另一条线追问“能力”的含义：SWE-Bench Illusion 指出模型在该基准上的高分部分来自记忆与学到的表面模式，而非可泛化的问题求解能力 [38]。

同时，评测开始跳出“修 issue”这一单一形态：SWE-Lancer 用来自 Upwork、总价值 100 万美元的 1400 多个真实自由职业任务（从 50 美元的缺陷修复到 32000 美元的特性实现，外加技术方案选型这类管理任务）度量模型的**经济价值** [39]；Terminal-Bench 转向命令行环境中的硬任务，用 89 个各自带独立环境、人工解法与验证测试的任务考察智能体在终端里的长程执行 [40]。度量本身也被重构：以“50% 任务完成时间跨度”为指标，把模型能力换算成人类专家完成同类任务所需时间，并观察到该时间跨度自 2019 年起大致每七个月翻一番 [41]。

最后是**现实效用的实证**。一项针对成熟开源项目、16 位有经验开发者、246 个任务的随机对照试验发现，允许使用 2025 年初前沿 AI 工具时，开发者的实际完成时间与他们的事前预期存在明显落差 [42]。这提示：基准解决率的提升与真实工程生产力的提升之间，仍不是简单的等号。

## 八、范式演进的四条判读

1. **评测定义任务，任务牵引方法**。三次跃迁（Defects4J [7]、HumanEval [13]、SWE-bench [25]）都是先有新的评测形态，方法才随之重组；而每一次跃迁之后，都紧跟一次“评测是否可信”的反思（[8] → [15] → [37][38]）。
2. **“执行”始终是这条脉络的硬约束**。从测试驱动的补丁验证 [4][7]，到 pass@k [13]，到智能体在容器里跑仓库测试 [25]，可执行验证既是能力上限的来源，也是评测失真的来源。
3. **智能体不是凭空出现的新物种，而是修复线与补全线的合流**。“生成—执行—读反馈—再生成”的闭环在 [18][19] 已经成型，智能体只是把这个闭环的动作空间从“改一段代码”扩到“操作整台机器” [26][29][30]，并把传统 APR 的定位—修复—验证流水线保留为内部结构 [27][28][31]。
4. **重心正在从“更强的模型”转向“更好的环境、数据与训练目标”**。2025 年后的代表工作大多在造环境与造数据 [34][35]、设计奖励 [36]，而不是设计提示词，这与领域路线图中“为智能体重构软件工程的参与者、流程、工具与产物”的判断一致 [45]。
