# 三技能评测：方法参考（打样）

> **定位**：这是一份参考实现的记录——我们如何为 paper-rebuttal / paper-review / paper-graph 三个技能构建评测集、如何跑评测、发现了什么。**它不是规范**。你们接手后怎么改、怎么走，由你们自己决定；这份文档的价值在于方法和踩过的坑可以复用。假定读者只有这份文档，没有其他上下文。

## 0. 背景：评测对象是什么，评测在测什么

**评测对象**是本仓库（EvoSkills）`skills/` 目录下的三个"技能"。技能 = 一个 `SKILL.md`（提示词+流程说明，有的附脚本），挂载给 LLM agent 后引导它完成特定任务：

- **paper-rebuttal**：收到审稿意见后，指导写作者回应（rebuttal）——诊断哪些意见驱动分数、归并共性问题、按优先级分配笔墨；
- **paper-review**：投稿前自审自己的论文——按检查表找缺陷（贡献、写作、实验、方法等5个方面）；
- **paper-graph**：给定研究主题或种子论文，产出领域谱系报告（挑战→方案的分类树 + 论文间"演化自"关系图，mermaid 绘制）。这个技能还带一套确定性 CLI 脚本（`skills/paper-graph/scripts/`），agent 按 SKILL.md 的 runbook 调用。

**评测要回答的问题**：挂上技能后，agent 产出是否比不挂技能更好？所以所有评测都是**双臂对照**：同一任务提示词跑两次——**base 臂**（裸模型）和 **skill 臂**（工作区挂载技能，模型可自行触发它）——报增量，不报绝对分。绝对分测的是底座模型的能力，增量才是技能的贡献。

**执行方式**：用 `claude` CLI 的无头模式（`claude -p`，单条命令跑完一个 agent 任务并退出）作为执行器。被测模型（SUT）可以是 CLI 能调用的任何模型——我们此前用的是 GLM-5.2（经代理接入）；判分里的 LLM 裁判（judge）用的是 Claude 系强模型（opus）。裁判与被试分离是有意的。

**目录约定**：仓库根 = EvoSkills 克隆。`skills/<名字>/` 是技能本体（你们的优化对象）；`tests/` 是评测的一切，**通过 git 交接给你们维护**。两点背景：(1) 公开代码会进未来 LLM 的训练语料，GT 是答案册，可能被下一代模型"背过"——我们的对策不是藏，而是**按模型代际刷新评测集**：构建全程脚本化可再生（候选池 dump、case 构建器、缺陷分类法与出题流程、GT 核验脚本俱在），换 SUT 代际时重铸一批新 case 即可，旧集用于回归、新集用于对比；(2) 无论仓库公私，`tests/.env`（真实 API key）、`harness/.venv`、`harness/runs/`（体积大且可重跑再生）不入库。

**一个兼容性细节**：技能 frontmatter 里的 `allowed-tools` 写的是另一套 agent 框架（EvoScientist）的工具名，Claude Code 不认识，执行器挂载技能时会自动删掉这一行（见 `run_case.sh` 内注释），技能内容本身不动。

## 0.5 术语与缩写表

| 术语 | 含义 |
|---|---|
| SUT | System Under Test，被测系统——挂/不挂技能的那个 agent+模型 |
| GT | Ground Truth，真值——判分依据的标准答案 |
| base 臂 / skill 臂 | 双臂对照的两条：裸模型 vs 挂载技能 |
| harness | 评测工装总称：执行器 + 判分脚本 + 汇总，都在 `tests/harness/` |
| case | 一个评测样例（一道题）：输入 + 任务提示词 + 真值 |
| checker | 确定性判分脚本（纯程序规则，不调用 LLM） |
| judge | LLM 裁判——处理必须语义理解的判分（命中匹配、质量分级、盲评） |
| fixture | 冻结输入——预先跑好并存盘的中间结果，让 SUT 从固定起点出发（隔离无关方差） |
| transcript | `claude -p` 的逐事件运行日志（`transcript.jsonl`），含每次工具调用——技能是否被触发、有无违规联网都从它审计 |
| e2e | end-to-end，端到端（相对于只测某个中间步骤的"微基准"） |
| pilot / 冒烟 | 小规模试跑，先验证管线再上全量 |
| S2 | Semantic Scholar——学术图谱 API，查论文元数据和引用关系（`tests/.env` 里配 `S2_API_KEY`，免费申请） |
| OpenReview | ICLR 等会议的公开评审平台：评审、分数、作者回应、最终决定都公开可查 |
| AC / metareview | Area Chair（领域主席）/ 其撰写的决定意见书——里面写了哪些审稿意见真正决定了录用与否，是 rebuttal 评测最硬的真值来源 |
| Oral / Poster / Reject / borderline / split | 论文结局分层：口头报告（高分录用）/ 海报（普通录用）/ 拒稿 / 分数在录取线附近 / 审稿人分数严重分歧（如 2,2,4,8） |
| champion | rebuttal 技能的术语：分数最高、最可能在讨论期为论文辩护的审稿人 |
| FP | False Positive，误报——review 评测里指"对论文的批评在事实上不成立" |
| mermaid | 文本描述的绘图语言（写在 markdown 代码块里渲染成流程图），paper-graph 的输出格式 |
| pymupdf / pymupdf4llm | PDF 转文本/markdown 的 Python 库，case 构建用 |

## 2. 方法主线（可迁移的核心）

给一个技能建评测，我们每次都回答同三个问题：

**① 真值从哪来？** 三个技能三种答案——
- **天然真值**（rebuttal）：OpenReview 有完整链条：评审+分数 → 真实作者 rebuttal → 分数变化 → metareview → 决定。metareview 尤其宝贵：AC 替你标好了哪些意见真正驱动分数，我们的"分数驱动意见集"GT 就以它为锚。
- **注入真值**（review）：这里其实存在一个"现成 GT"候选——真实审稿意见（拿 ≥2 名审稿人共提的弱点当真值，测 self-review 能预判多少）。我们没用它做主力，因为四个问题：真实评审只列"足以定分数"的弱点、不枚举全部问题，**召回率的分母不成立**；模型发现与自然语言弱点的对齐处处是模糊语义匹配，判定标准难以机判；评审公开在网上，SUT 可能见过（污染）；难度不可控、也没有干净对照。所以改为**自己造真值**——往干净论文里埋已知缺陷：分母精确（埋 N 个就是 N）、判定标准手写可机判、缺陷是新造的天然免污染、v0/v1/v2 难度分层可控。代价是要保证"缺陷自然、判定标准可机判、与原文不冲突"，我们用多智能体流水线（出题 agent + 对抗验证 agent + 人工终审）保证质量——你们复现时用任何等价流程都行。生态效度版（真实评审当 GT）仍是可选的补充路线。
- **专家真值 + 联网核验**（graph）：谱系边先凭领域知识写，再**逐条**用引用关系（目标论文是否真的引用了来源论文，S2 查询 + PDF 兜底）和时序（arXiv 编号前四位就是投稿年月）核验。原则：凡是能核验的绝不停留在"我记得"。

**② 什么用脚本判，什么用 LLM judge 判？** 分界线只有一条：**能程序判定的绝不用 judge**。为此不惜改造输入——最典型的一招是把每条评审意见**预编号**（R1.W2 = 审稿人1第2条弱点），并要求 SUT 在输出中引用编号，"共识识别对不对"就从语义比对降级成集合运算。judge 只保留三类躲不开的语义判断（命中匹配、质量分级、盲评偏好），且全部套同一纪律：**判决必须附逐字引文 → 脚本机械核验引文确实存在 → 核不过自动作废降级**（防裁判编证据）。盲评另加两轮 A/B 位置交换，两轮不一致记平局（防位置偏好）。

**③ 测什么？** 见 §0 的双臂定义。补充一点：任务提示词对两臂**必须完全相同**且各技能内含**输出格式契约**（如 rebuttal 要求按编号回应、graph 要求特定的边写法）——这样判分脚本对裸模型臂同样适用，双臂比的是内容质量而非格式运气。

## 2.5 指标分层框架（§2 的补集：一个技能该配齐哪几类指标）

§2 的三问回答"单个指标怎么造"，这一节回答"一个技能的指标体系怎样才算配齐"。框架是三个技能的评测做完之后向回提炼的（不是先有框架再做评测）；用它反过来审计现有指标的过程和结果记录在 §3.6。

指标按**抽象层级**分四层——从"整体好不好"到"哪一步坏了"，每层回答不同的问题、扮演不可互替的角色：

| 层 | 回答什么问题 | 角色 | 实例化时的设计问题 |
|---|---|---|---|
| **L1 结果层** | 盲评下，交付物的"消费者"更喜欢哪份？ | 防 Goodhart 锚点——抓"下层指标涨了、东西反而变差"。**不自动是头条** | 消费者人设是谁（AC/作者/研究者）？裁判本身拿什么校准（人工台账/天然结局）？ |
| **L2 能力层** | 在定义任务的各维度上有多好？ | 版本间回归跟踪；头条数字通常在这层 | 真值从哪来（§2 ①）？每个维度的分母站不站得住？ |
| **L3 机制层** | 技能内部哪个阶段该为 L2 的数字负责？ | 修理清单的直接来源；技能迭代的"梯度" | 流水线哪些阶段可分离？每个阶段用哪招隔离（见工具箱）？ |
| **Gate 门槛层** | 产出是不是一份合法交付物？ | 有效性底线——让上面所有指标可解释（对结构非法的产出谈召回没有意义） | 什么输出契约能让违规被纯脚本检出？ |

**L3 隔离工具箱**（四招）：

- **冻结上游**：上游跑一次存 fixture——既直接度量了该阶段，又让下游从固定起点起跑（实例：graph 检索冻结）；
- **阶段微基准**：绕开完整流程，给单个阶段喂一组已知答案的受控样本（实例：graph edge_bench）；
- **喂真值消融**：把某阶段的输入换成 GT——上游"完美化"后剩下的缺陷全归下游（实例：rebuttal 拟议中的"喂 GT 分析给写作步"，见 §3.6）；
- **数据轴分桶**：阶段不可分离时的退路——按输入切片分桶，用"哪类输入上败"近似"哪个环节败"（实例：review 召回按缺陷类型分桶）。

**层级本身只是分类学；让它成为系统的是四条纪律**：

1. **逐格填或弃权**（fill-or-waive）：给新技能配指标时，四层逐格要么实例化出指标、要么写下弃权理由（如"无可分离阶段"）。空着不写理由不行——这条把"给新技能设计评测"从发明题变成填表题。
2. **跑之前声明头条**：每技能只有一个头条数字，放在**离该技能构念最近的层**——rebuttal 的构念（说服）天然整体，头条在 L1；review/graph 的构念可分解且 GT 干净，头条在 L2。事先声明，防跑完之后挑好看的层报。
3. **相邻层背离是一等发现，不是麻烦**：范例即 rebuttal 先导——L2 分数驱动召回 0.69→0.96 而 L1 盲评 1 负 2 平，背离本身把问题定位到了分析之后的写作策略（§6）。采纳框架 = 承诺解释每一次背离，不许只引用对自己有利的那层。
4. **成本金字塔定节奏**：Gate+L3 便宜、样本量大 → 每次迭代都跑（驱动改进）；L2 中等 → 每次版本对比跑；L1 贵、样本量小 → 里程碑跑。其中人工台账（`tests/human-eval/`）的角色是**校准 LLM 裁判本身**——人机判决一致率够高，便宜裁判才有执照在后续轮次替人。

**适用边界**：模板从 n=3 个"产出学术工件"型技能提炼；遇到结构迥异的技能（如翻译类——L2 有现成指标传统、内部阶段完全不同）预期要修订一次。当 v1 用，别当普适规范。

## 3. 各技能构建过程速记

**rebuttal**（真值最顺，先做它验证整套方法）：从公开聚合源拉 ICLR 2026 全量池（`harness/pool/`）→ 按结局分层选样 → 用**评审公开前**的 arXiv 首版转档（防论文正文已含评审反馈）→ 评审意见切分预编号 → 人工标 GT（分数驱动集以 metareview 实际引用的理由为锚）。反爬全程折腾：arXiv API、OpenReview REST、openreview-py 依次被封，最后 metareview 靠真浏览器渲染页面拿到——见 §5 坑。

**review**：选 5 篇 ICLR 2026 录用且评审前 LaTeX 可得的论文 → 定缺陷分类法（`DEFECT_TAXONOMY.md`）→ 多智能体并行出题（每篇一个设计 agent 通读全文产出注入补丁，验证 agent 机械核查每个补丁在原文唯一定位、读起来自然、与原文既有问题不冲突）→ 落盘时二次机械核验 → 人工终审抽查。v0 干净对照必须有：真论文本来就有真缺陷，"批评属实 ≠ 误报"这条设计后来被冒烟数据证明关键（v0 的 44 条发现 43 条经核查是正当批评）。

**graph**：8 个查询刻意避开技能文档自带的示例领域（技能作者调试时用过的例子≈训练样例，测它会高估）→ 锚点/边全部联网核验 → **检索冻结**（技能流程的检索步跑一次存 fixture，后续评测从固定论文池起跑——冻结动作本身就产出了第一个发现：检索层锚点召回仅 16.4%）→ 微基准单测审计步（40 对，负例按难度分四层：跨域哨底/并行同门/错轴归因/时序反向）→ e2e 双臂同提示词含输出契约。

## 3.5 各技能评什么、怎么判（指标体系）

**rebuttal**（确定性判分 `check_rebuttal.py`；judge 模式 `fab` / `quality` / `pairwise`）。被测 Agent 产出两个文件：`analysis.json`（策略分析）+ `rebuttal.md`（正文，每段用 `Addresses: R1.W2` 标记回应对象）。四个维度：

| 维度 | 怎么判 |
|---|---|
| 诊断准确性 | 脚本：分数驱动意见识别的查准/查全（对照 `gt/score_driving.json` 的 high 集）、共性主题归并（编号集合交集 ≥2 即命中）、最友好审稿人识别 |
| 执行纪律 | 脚本：全意见覆盖率（Addresses 标记齐不齐）、字数预算是否向高优先级意见倾斜 |
| 诚实性 | 混合：脚本先扫"回应中出现、论文中不存在"的数字 → judge `fab` 逐个裁决（论文可推导 / 外部事实 / 捏造） |
| 说服力与质量 | judge：`quality` 对每条高优先级意见判 resolved / partial / evaded；`pairwise` 双臂盲评（裁判扮演 AC 判哪份更可能改分，双轮位置交换） |

**review**（结构判分 `check_review.py`；judge 模式 `review-match` / `review-fp`，**必须先 match 后 fp**）。产出 `findings.json`（结构化发现列表）+ `self_review.md`。两个核心指标：

| 指标 | 怎么判 |
|---|---|
| 缺陷召回率 | judge `review-match` 按每个注入缺陷预写的 detection_criteria 逐一判 HIT / PARTIAL / MISS（判决须引用发现原文，脚本核验，核不过降为 MISS）→ 脚本汇总 strict / lenient 召回，可按缺陷难度与类型分桶 |
| 误报率 | judge `review-fp` 审计未命中任何缺陷的发现：legitimate（论文确有此问题，不算错）/ fabricated（与原文事实矛盾，计误报，须附原文反证引文）/ subjective（无可证伪断言）→ `fp_rate_major`；v0 干净对照组专测误报底线 |

**graph**（确定性判分 `check_graph.py`；judge 模式 `graph-taxonomy` / `graph-edges`；另有独立微基准）。产出 `output/report.md`（按输出契约：分类树 + 逐方案演化图 + 论文附录）。脚本是绝对主力：

| 维度 | 怎么判 |
|---|---|
| 结构合法 | 脚本：每个 mermaid 块可编译；图中论文编号无凭空捏造（都能对回论文池） |
| 边的事实性 | 脚本：每条"B 演化自 A"核验 B 是否引用 A（S2 按 ID → 按标题 → 下载 PDF 查参考文献，三级都失败记 unverifiable 而非 fail）+ 时序合法（B 不早于 A） |
| 覆盖率 | 脚本：锚点论文召回、经典演化边召回（对照 `gt/queries.json`） |
| 语义质量 | judge：`graph-taxonomy` 对照参考分支框架给三维锚定分（分支覆盖/归组连贯/粒度）；`graph-edges` 对抗式抽查 ≤10 条边（默认边是错的，文本证据成立才判 holds） |
| 审计环节单测 | `edge_bench/` 微基准：绕开完整流程，直接测技能内部证据审计对 40 对真/假演化关系的判别力（真边存活率 + 假边拒绝率） |

各指标在运行汇总表里的列名映射，见附录 B 对应技能小节。这套指标按 §2.5 四层框架的归类、以及审计出的缺口清单，见 §3.6。

## 3.6 对照框架审计现有指标：推导过程与缺口矩阵

2026-08 用 §2.5 的框架对 §3.5 的既有指标做了一次逐格审计。本节记录两件事：缺口矩阵本身，和**矩阵是怎么推出来的**——后者更值钱，因为审计过程对任何新技能可重放。

### 推导过程（四步，可重放）

1. **归类**：把 §3.5 里每个现有指标归入四层之一。归类本身就出信息——哪些格子有人、哪些空着，一眼可见（见下矩阵）。
2. **对空格问该层的设计问题**（§2.5 表格第四列）：对着两样东西问——技能的流水线结构（SKILL.md 的步骤划分）和手头的真值资产。能实例化出指标就记候选，不能就记弃权理由。
3. **拿已知疑难回放**（关键一步，高价值缺口全出自这里）：把已有发现里悬而未解的现象逐个拎出来，问"**四层里哪个格子的指标本可以解释它**"：
   - rebuttal L2 大涨、L1 持平（§6）——现有指标没法判定输在分析还是写作 → 暴露 L3 写作步未隔离，以及 L1 裁判自身未校准；
   - review 两臂共同盲区（失效引用键等，§6）——分不清是"找不到"还是"认不出" → 暴露 L3 整层缺失；
   - graph 是反面印证：检索与审计两步**因为有 L3 格子**，§6 里它们的问题都自带修理方案落地；而中段三步（classify/outline/detail）没有格子——e2e 边召回一旦跑出来偏低，将说不出边死在哪一步 → 中段盲区是缺口。
   能解释疑难的空格 = 高优先缺口；谁的疑难都解释不了的空格降级或弃权。**缺口不是瞪着空表格瞪出来的，是拿疑难倒逼出来的。**
4. **排序 + 显式弃权**：每个候选标 fill / defer（⏸）/ waive（🚫）三态，waive 必须带理由——这是防指标动物园的闸门（报表每多一列，读者对"哪个数字是主张"就多一分困惑）。

### 缺口矩阵

| 层 | rebuttal | review | graph |
|---|---|---|---|
| L1 结果层 | ✅ pairwise（AC 人设）；❌ 裁判校准 | ❌ 整格缺失（盲评 pairwise） | ✅ pairwise + 人工台账已建（台账未判 = 执行欠账，非设计缺口） |
| L2 能力层 | ✅ 四维度齐 | ✅ 召回 + 误报 + v0 对照；🚫 严重度校准 | ✅ 覆盖/事实性/语义质量齐 |
| L3 机制层 | ✅ 分析步（analysis.json 直接判分）；⏸ 写作步 | ❌ 整层缺失（片段微基准 + aspect 字段） | ✅ 检索步 + 审计步；❌ 中段边漏斗 |
| Gate 门槛层 | ✅ 文件/标记/编造数字扫描 | ✅ schema 校验；❌ 引文存在性机检 | ✅ 编译/编号/时序 |

### 缺口明细（按补齐优先级）

1. **graph 边漏斗**（L3）：端到端边召回把四种死法混为一谈。补法——对每条 GT 边记录死在哪一站：classify 后仍可表达（两端论文归入同一方案分支，否则逐方案演化图里画不出这条边；此前控制论文数 N 的对照实验已发现"分类法阻断演化边"是质量瓶颈，这条指标把该发现常态化为常设监测）→ detail 里被提出 → audit 存活 → 进终稿。逐步产物按 runbook 落盘在 ws 里，原则上对既有运行免模型重打分；最坏情况重跑冻结池 case。近乎免费，解开最大的归因混淆。
2. **review 盲评 pairwise**（L1）：作者人设——"投稿前你更愿意收到哪份自审"。守住"召回涨了、产出却变成没人想读的清单"这类 Goodhart 失败。盲评管线已通用化（`blind_prep_models.py` / `run_pairwise_matrix.sh` / `pairwise_tally.py`），近乎免费。
3. **review 片段微基准**（L3）：把含缺陷的段落（带少量上下文）直接喂给审查逻辑，去掉全文搜索环节。e2e MISS × 片段 HIT = 找不到（覆盖协议问题）；两处都 MISS = 认不出（领域知识问题）——两种修法完全不同，现有的共同盲区发现无法区分二者。注入补丁 + 精确位置全在手，等于 review 版 edge_bench。顺手的小补：findings schema 加 `aspect` 字段（5 方面检查表的哪一面产出该发现），命中侧的阶段归因白捡。
4. **rebuttal 裁判校准**（L1）：三技能中唯一能拿**天然结局**（而非人工）校准 L1 仪器的机会——池子里有真实 rebuttal 与真实分数变化，测裁判能否挑出实际赢家。注意配对要控混淆：跨论文配对会混入论文本身质量差；更干净的是同一篇论文内跨审稿人线程（rebuttal 后谁的分数动了），或按单线程预测涨分方向。
5. **review 引文存在性 Gate**：findings 现在没有 verbatim quote 字段，编造发现只能靠 judge 误报审计（贵，且在 L2）兜底。契约加逐字引文字段 + 脚本 grep 原文，幻觉发现在花 judge 钱之前就被拦下。这是唯一需要动输出契约（提示词 + schema）的缺口——改完老运行数字不可比，宜与下一批 case 一起换版。
6. **横切三件**（三技能共缺）：**裁判-人工一致率**——人工台账的数据顺手就能算这个数，但从未定义成常设指标，它是"便宜 LLM 裁判有资格替人"的执照（§2.5 纪律 4）；**重复运行方差**——现在全部数字都是单次运行，每技能挑 2-3 个 case 跑 k=3 重复，给所有增量结论配误差棒（审稿人第一个问题的便宜保险）；**每份交付物成本**——token/轮次数躺在 meta.json / transcript 里没人汇总，summarize 加一列即可，skill 臂 vs base 臂的开销差是"工作流编排值不值"的必答题。
7. ⏸ **rebuttal 写作步 oracle 消融**（L3）：喂 GT 分析给写作步，可裁定盲评输在分析还是写作。需要新增模型运行，等真要动写作策略时再建。
8. 🚫 **review 严重度校准**（L2）：SUT 标的 major/minor 是否对得上注入难度档。决策价值低、徒增报表列，弃权。

**一条值得留底的观察**：三个技能各缺**不同的层**（rebuttal 缺 L1 仪器校准、review 缺 L1+L3、graph 缺中段 L3）。若框架只会制造忙碌，缺口应该均匀遍布；缺口集中且互不相同，说明审计找的是真窟窿。

## 4. 评测怎么跑

命令速查在附录 B（§1 rebuttal、§5.9 review、§5.95 graph、§5.5/5.8 judge）；附录 A 有新机器从零搭环境。要点三个：

1. 执行器产物结构统一：`runs/<批>/<case>-<臂>/{ws/, transcript.jsonl, meta.json, metrics.json}`。**transcript 是原始数据**（技能触发率、违规联网审计都从它来），metrics 是衍生物——checker 有 bug 修好后可以对既有 ws 免费重打分，不用重跑模型。
2. judge 全部可以用 `judge.py <模式> --case ... --run ... --model <你们的裁判模型>` 独立跑；盲评先跑 `blind_prep.py`（纪律：判决收齐前别打开 mapping.json）。
3. 三个技能互相零依赖，任意顺序/并行（同一账号并行会互抢限速）。

## 5. 踩过的坑（经验比规则值钱）

- **S2 数据有缺口**：有论文查无记录（Progressive Distillation），有论文引用列表不全（DoRA 的列表里居然没有 LoRA 原文）。引用类检查必须做降级链（按 ID → 按标题 → 下载 PDF 直查参考文献），否则会把真实的引用关系误判为不存在。
- **PDF 转档撕小数点**：pymupdf 会把 `9.99` 转成 `9 _._ 99`，我们的编造数字扫描一度全是假警报。对转档文本做数字比对前先归一化这类伪影。
- **误报审计必须排在命中匹配之后**：先判哪些发现命中了注入缺陷，剩下的才进误报审计，顺序反了会把该判命中的发现当误报审。
- **给裁判设"不确定"档要小心**：graph 审计步有个 INFERRED（存疑保留）档，微基准里 13 个漏网假边有 11 个走了这条道——"不确定"会变成假信息的庇护所。要么收紧定义（仅主题相似 → 直接拒绝），要么下游对该档单独处置。
- **反爬要备多条路**：某个 API 被封时，官方 SDK、网页渲染、PDF 端点往往各有一条活路；礼貌退避 + 增量缓存让重试可断点续跑。
- **机械切分有伪影**：按条切分评审意见会把参考文献列表、"愿意涨分"的表态切成独立意见，污染覆盖率的分母。切分结果要人工过一遍。
- **防污染三件套**：不用技能文档自带的示例当测试样本；底稿选 SUT 训练截止之后的论文；埋的缺陷是新造的（世界上不存在的错误不可能被背出来）。

## 6. 已有发现与基线数字（这套方法产出了什么）

| 技能 | 增量证据（base 臂 → skill 臂） | 结构性发现 → 技能修理清单 |
|---|---|---|
| rebuttal（先导 n=3） | 分数驱动意见召回 0.69→0.96；共识检出 9/11→10/11；笔墨预算向高优先级移动 | 盲评 1 负 2 平：技能教"新实验胜过解释"导致回应里堆满"待补实验"的承诺，而扮演 AC 的裁判系统性奖励"从论文里挖既有证据"。**改进方向：提新实验之前先挖已有证据** |
| review（冒烟 n=3） | 缺陷召回 0.33→0.68；误报两臂近零（113 条审计仅 2 条不实）；v0 对照 43/44 判正当批评 | 两臂共同盲区：失效引用键、数据泄漏式实验设置、表格规范类缺陷 |
| graph（微基准+检索层；e2e 待跑） | e2e 待跑 | ① 检索层是瓶颈：锚点召回 16.4%，把检索预算扩大三倍也只从 0/9 提到 1/9——是相关性排序偏向近期衍生文的问题，不是预算问题 → 需要种子论文引用图扩展、引用数感知排序；② 审计步：真边 20/20 存活但假边仅拒 7/20（INFERRED 逃生舱 + 审计模板不含出版年份、时序反向查不出来） |

判分裁判此前由 Claude 系模型担任（被试是 GLM-5.2，裁判与被试不同家族，不存在自评偏好）。你们换裁判模型没问题，但同一轮对比内裁判必须一致。

## 7. 交接后

以上全部是参考。沿用、改造、推翻都随你们。只有两条建议（是建议不是规则）：

1. 如果你们会拿数字做前后对比：测量仪器（checker / judge 提示词 / GT）在一个对比周期内保持不动，否则数字不可比；
2. 如果你们会反复对着评测集改技能：留一部分 case 平时不碰、只在里程碑时跑，防止把技能优化成"这 33 个 case 专用"。

有对评测集本身的修改想法，直接改——它现在是你们的了。
